# 固定不改原则

经过任务修改、优化、审查和测试通过之后的**改好的内容就固定不改了**。

## 例外情况

**只有以下情况才允许修改已固定的代码：**

1. **出现了问题** - 发现bug或错误需要修复
2. **后续任务涉及** - 新需求明确要求改动该模块
3. **用户明确同意** - 获得用户授权后才能修改

## 验证标准

**代码在固定前必须经过：**

- ✅ 多次代码审查
- ✅ 功能测试验证
- ✅ 模拟用户使用场景
- ✅ 边界条件测试
- ✅ 集成测试通过

## 为什么需要固定不改

1. **稳定性** - 避免反复修改导致回归问题
2. **可预测性** - 系统行为保持一致
3. **专注优化** - 把精力放在策略优化而非基础设施
4. **降低风险** - 减少引入新bug的机会

## 如何处理新需求

**遇到新需求时：**

1. **评估影响范围** - 是否涉及已固定模块
2. **寻找替代方案** - 优先在未固定区域实现
3. **征求用户同意** - 如必须修改，详细说明理由和风险
4. **完整验证流程** - 修改后重新走一遍验证流程
