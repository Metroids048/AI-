## BLOCKING DECISION — the E-010 premise was wrong

The operator asked to make Testnet positions "more aggressive": ~5% of equity
notional (~360 USDT) at 50x, believing the current size was ~60 USDT.

**Measured live (2026-08-12 04:25Z, equity 7358.99 USDT):**

| Symbol | Notional | % of equity | Leverage | Margin |
|---|---|---|---|---|
| BTC/USDT | 2572.63 | 34.96% | 40x | 64.32 |
| ETH/USDT | 2579.94 | 35.06% | 40x | 64.50 |
| total | 5152.57 | 70.02% | | 128.82 |

**The "60U" is margin, not position size.** 64.32 USDT margin is what the account
screen shows. Actual notional is ~2572 USDT.

Consequences, both verified:

1. **exposure 0.35 → 0.05 is a ~7x REDUCTION** (2572 → 367 USDT notional; margin
   64.32 → 7.35 at 50x). It is the opposite of "more aggressive".
2. **Raising leverage alone cannot enlarge the position.** `_calculate_quantity`
   returns `min(risk_notional, equity*exposure, equity*leverage)`. While the
   exposure cap binds, 40x and 50x resolve to an *identical* notional. Leverage
   only frees margin. Pinned by
   `test_s005_leverage_raises_capacity_without_inflating_notional`.
3. **exposure 0.05 stalls the entry chain.** BTC 34.96% and ETH 35.06% both exceed
   0.05, so `Gatekeeper._evaluate_numeric_risk` rejects every new entry for both
   symbols with `max_symbol_exposure_exceeded` until they exit on their own
   stop/target. Existing positions are never reduced or closed — see the safety
   proof below — but no new entry is admitted. This collides with the operator's
   stated hard requirement that the chain stay connected.

To make positions **larger than today**, exposure must go **above 0.35**. That was
never authorized. This is why nothing was applied.

The script is now parameterized so any decision is one command:

```bash
# what the operator literally specified (7x smaller, stalls entries)
python scripts/apply_e010_testnet_sizing_profile.py --leverage 50 --exposure 0.05 --apply

# leverage only, size unchanged, chain unaffected
python scripts/apply_e010_testnet_sizing_profile.py --leverage 50 --exposure 0.35 --apply
```

Caution on the second form: `set_leverage` fires at entry submission
(`services/automated_trading/infrastructure/binance_adapter.py:321`). Raising
leverage on a symbol that already has an open position moves that position's
liquidation price closer. Entries are currently exposure-blocked so it would not
fire until a position closes — but confirm before relying on that.

## SAFETY PROOF — exposure cap never touches existing positions

The operator's gate condition was: *if lowering the cap could reduce or close an
open position, do not apply it — report it as a safety block instead.* Five
independent pieces of evidence say it cannot. **Do not re-derive this.**

1. `max_position_fraction` has exactly one functional consumer in the V2 chain —
   `services/automated_trading/application/cycle_service.py:619`
   (`exposure_ceiling = equity * request.max_position_fraction`), inside
   `_calculate_quantity` (defined at :589).
2. `_calculate_quantity` has exactly one call site repo-wide —
   `cycle_service.py:1711` (`entry_notional = _calculate_quantity(...)`), in the
   entry path after `INTENT_CREATED`.
3. `max_symbol_exposure` has one enforcement point —
   `services/execution/gatekeeper.py:338`:
   `projected_symbol_exposure = risk_state.symbol_exposure + requested_fraction`
   (:334) then `rejection_reasons.append("max_symbol_exposure_exceeded")`. The
   output is a **rejection of a new entry**, never a reduce/close action.
4. That check lives in `_evaluate_numeric_risk` (:313), called **only** from
   `validate_entry` (:157). `validate_reduce_risk_exit` (:234) does not call it —
   its rejections are reduce-only semantics, quantity bounds, side match, fencing,
   exchange availability. **A tightened cap can never block an exit.**
5. `services/automated_trading/application/exit_service.py` contains no reference
   to `exposure` / `max_position_fraction` / `max_symbol_exposure` / `leverage`;
   `risk_profile_sweep` in `services/execution/tasks.py` has no close/reduce/submit
   in its body.

Locked as 5 regression tests in
`tests/automated_trading/application/test_e010_aggressive_sizing.py::TestE010ExposureCapNeverTouchesExistingPositions`.
They assert on source structure, so they fail if a new consumer or call site is
introduced.

Also verified: 50x is available on Testnet — queried `testnet.binancefuture.com`
leverage tiers, BTC max **125x**, ETH max **100x**. No
`EXTERNAL_LEVERAGE_LIMIT_BLOCKED` risk.

And: `shared/models/risk.py::PAPER_RUNTIME_LIMITS` still reads
`risk_per_trade 0.10 / max_leverage 40.0 / max_symbol_exposure 0.35` — production

## OPEN BUG — long/short direction mismatch (found, not fixed)

`/api/v1/runtime/reconciliation` returns `status: degraded` with
`entry_blocked_symbols: ["BTC/USDT", "ETH/USDT"]`, while the cycle's own
per-symbol `reconciliation_status` in `logs/scheduler-state.json` is `HEALTHY`.
This is **persistent, not transient** (an earlier "transient" explanation was
wrong and is retracted below).

Root cause is in the `mismatch` payload — exchange says long, local DB says short:

```json
"exchange_only_positions": [
  {"symbol": "BTC/USDT", "side": "long"},
  {"symbol": "ETH/USDT", "side": "long"}
],
"local_only_positions": [
  {"symbol": "BTC/USDT", "side": "short"},
  {"symbol": "ETH/USDT", "side": "short"}
],
"quantity_mismatches": [],
"consistent": false
```

Quantities agree; only direction disagrees. The exchange side is certainly correct
— BTC entry 63757.90 → mark 63837.00 with **positive** unrealized PnL is only
consistent with a long.

Two candidate causes, not yet distinguished:

- **(a) Comparison bug** — direction normalization differs between the exchange
  payload (`side: "long"`) and the local enum, so every position looks like two
  half-matches. If so, this is a UI-truth defect in the projection endpoint and
  belongs to this task's scope.
- **(b) Stale local rows** — old short rows never marked CLOSED, with the current
  longs having no matching local row. If so it is a data-integrity issue.

Where the investigation stopped: `scripts/inspect_position_truth_mismatch.py`
crashed on `AutomatedTradingRepository.list_positions` — **that method does not
exist**. Find the correct accessor (`_local_open` / `_exchange_linked_positions`
are used at `apps/api/routers/runtime.py:450-456`) and print the local rows with
their `management_status` and direction.

Why this matters beyond cosmetics: the ETH protection orders on the exchange are
`SELL` + `reduceOnly: true` (correct for a **long**). If any code path trusted the
local `short`, a "protective" order would be directionally wrong. **Verify the
protection-order direction logic reads exchange truth, not the local row, before
closing this out.**

Note: this endpoint's `blocked_symbols` is a read projection for the UI. The
cycle's own reconciliation (HEALTHY) is what actually gates trading, which is why
the chain kept running cleanly for 150 cycles. Confirm that separation holds —
if the projection ever feeds back into gating, the blast radius is larger.
