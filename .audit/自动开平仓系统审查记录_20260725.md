## 发现并修复的问题

### 1. 手动持仓污染drawdown计算（P0严重bug）
**问题描述**：
系统在计算策略回撤时，将手动开的ETH持仓（0.086 ETH short，浮亏约-110 USDT）计入策略权益，导致：
- `account_equity`被污染（实际策略权益应该更高）
- `drawdown_pct`被虚高（触发错误的风控拒单）
- `hard_drawdown_limit`（20%）面临误触发风险，会强制平掉策略持仓并锁死整个run

**影响范围**：
三条独立的drawdown判断路径全部受影响：
1. `services/execution/tasks.py` 的`risk_profile_sweep`（后台扫描，每分钟）
2. `services/execution/paper_signal.py` 的`_build_risk_state`（每个调度周期，信号生成前）
3. `services/execution/paper_cycle_orchestrator.py` 的`_is_hard_drawdown_locked`（每个调度周期，最严重，会锁定策略）

**修复方案**：
新增`services/execution/account_equity.py::resolve_manual_position_pnl()`函数，从`gateway.reconcile()`读取交易所持仓，识别`management_status != 'MANAGED_STRATEGY'`的手动持仓，计算其unrealized_pnl并从`account_equity`中扣除。

三处调用点统一改为：
```python
manual_pnl = resolve_manual_position_pnl(
    paper_run=paper_run,
    execution_repo=self.execution_repo,
    gateway=self.gateway,
)
strategy_equity = raw_account_equity - manual_pnl
```

**验证状态**：
- ✅ 代码语法验证通过
- ✅ 导入链路验证通过
- ✅ 服务重启后调度器恢复正常（14:57/15:00周期成功完成）
- ⏳ 等待真实开仓订单验证修复生效（监控中）

### 3. ReduceOnly Order rejected问题（非bug，设计trade-off）
**问题描述**：
71条`ReduceOnly Order is rejected`错误，集中在SOL/USDT、BTC/USDT、ETH/USDT

**根因分析**：
本地认为持仓存在（`active_positions`），但Binance侧已平仓（被止盈/止损条件单触发），产生短暂不同步。

**现有机制**：
`services/execution/paper_exchange_execution.py::reconcile_local_positions_with_exchange`第891-927行已有完整的2周期防抖清理逻辑：
1. 第1次发现缺失：记录`reconcile_missing_counts[symbol]=1`，等待下一周期
2. 第2次确认缺失：调用`close_position_fn`关闭本地幽灵记录，清理干净

**结论**：
这是合理的防抖设计（防止网络抖动误判），副作用是**第一个周期会产生1次ReduceOnly拒绝**，可接受。真正需要监控的是`gateway.reconcile()`失败率——如果它经常失败（网络/API问题），会阻止清理逻辑运行。

**验证状态**：
- ✅ 代码审查确认机制健全
- ✅ 当前`exchange_missing_position_counts={}`，无累积幽灵记录

### 审查通过的关键链路
**开仓链路**：
信号生成(`paper_signal.py`) → 风控预检(`_build_risk_state`) → gatekeeper(`gatekeeper.py::submit_order`) → 网关下单(`gateway.py`)

**平仓链路**：
止盈止损触发(`exit_ladder.py::level_hit`) → 构建平仓单(`_close_order_request`, `close_only_mode=True`) → gatekeeper（**跳过numeric risk检查**，平仓不受drawdown限制） → 网关执行

**对账链路**：
`reconcile_local_positions_with_exchange` → 2周期防抖 → 清理幽灵持仓

**硬回撤锁定**：
`_is_hard_drawdown_locked` → 强制平仓 → 锁定run（`paper_status='locked'`）

## 遗留注意事项

### 1. strategy_equity_peak持久化分歧
`_is_hard_drawdown_locked`和`risk_profile_sweep`独立计算`strategy_equity_peak`，前者只在内存用，后者会写回数据库。两处都调用`resolve_manual_position_pnl`，理论值一致，但略有计算时差。

**影响**：无，这是设计上的独立评估，不是bug。

### 2. gateway.reconcile()性能
每个调度周期最多调用3次（tasks.py后台 + paper_signal.py + paper_cycle_orchestrator.py），每次都是同步HTTP请求，可能累积延迟。

**建议**：如果发现周期耗时持续超过120秒，考虑：
- 在周期入口处调用一次，缓存结果传给三处
- 或者在`resolve_manual_position_pnl`内部加60秒缓存

### 3. 手动持仓识别逻辑
当前依赖本地`position_records`的`management_status`字段匹配，如果对账逻辑有bug（漏标记手动持仓），会导致手动持仓被误认为策略持仓。

**风险**：低，对账机制已运行数月，未见此类错误。
