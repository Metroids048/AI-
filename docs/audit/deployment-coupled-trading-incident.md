# 部署耦合型突发交易事故专项报告

日期：2026-07-22
范围：Binance Simulation/Testnet、Paper 调度器、订单审计与运行时部署
结论：事故由“验收流量与策略流量混用”叠加“调度器缺少跨进程唯一领导权”造成；并非单一风控阈值过严。修复未调整任何风控、止损止盈、杠杆、仓位或 net-edge 准入数值。

## 1. 事故定性

2026-07-21 11:03（Asia/Shanghai）的 BTC/ETH 秒级开平仓是 Testnet acceptance 的固定往返验收行为。代码证据显示 `scripts/run_testnet_acceptance.py` 原先无需人工确认，且每次生成新幂等键；历史 Codex 任务又明确执行过该脚本。因此 Agent 的“验证动作”直接产生了外部模拟盘订单。

11:18 的 BTC 订单包含真实策略开仓及保护单，但后续对账把无法恢复来源的交易统一写进 `binance_demo_audit_only`，造成验收流量、策略流量和人工流量在历史账本中外观相同。18:38 再次出现 BTC/ETH 成对开仓、保护单、立即平仓的验收形态。用户记忆中的“16 点”与账本交易时间不完全一致；16:26–16:52 确有 Agent 代码提交，但账本第二个外部订单簇是 18:38。该差异已保留，未强行归因。

## 3. “其余时间没有反应”的真相

账本并非整晚完全停止。11:18 至 18:38 之间有 333 条决策记录；18:38 至 20:14 有 30 条；20:20 至账本末尾有 245 条。最近一天的 643 条决策中，主要阻断为：ensemble discarded 258、technical signals insufficient 206、LLM veto 126、multi-timeframe disagreement 50；没有 gatekeeper 数值门槛拒绝占主导的证据。

因此应区分：

- 调度活性：有持续决策，说明主循环在运行。
- 订单活性：大部分决策未通过策略/集成/LLM 层，因而没有新订单。
- 早期 7–8 小时空窗：7 月 18、19 日历史账本存在 481.289、459.545 分钟周期缺口，说明旧部署确有进程/调度生命周期不稳定问题。

周期与阻断证据分别见 `artifacts/cycle-liveness.csv` 和 `artifacts/blocker-after-burst.csv`。

## 4. 根因树

1. 直接原因：验收脚本默认可执行外部订单，Agent 的测试动作与生产型外部副作用没有隔离。
2. 放大因素：验收脚本每次随机生成幂等键，同一验证可重复制造真实模拟盘往返单。
3. 部署因素：8000 的一体化引擎和 8016 的控制台外置调度器可同时连接同一 SQLite 库，原系统没有 DB/Redis 领导租约。
4. 幂等缺口：`processed_cycle_keys` 只保存在 PaperRun JSON 中，没有数据库唯一约束，两个进程可同时通过内存检查。
5. 启动耦合：Paper 周期继承 `run_immediately=True`，每次 Agent 重启/部署都会立刻执行一个交易周期。
6. 审计缺口：旧订单没有 `order_origin/run_mode/test_run_id/deployment_sha/scheduler_instance_id` 等字段，对账导入进一步抹平来源。
7. 性能因素：所有 PaperRun 串行执行，一个周期曾持续数小时，外观上像“系统沉默”，也增加重启重叠风险。

## 5. 已实施修复

- Testnet acceptance CLI 和 API 均要求显式 `execute_external_orders` 与非空授权原因；缺失时在构造交易所网关之前拒绝。
- Paper 调度首次运行改为等待完整周期，不再因进程启动立即触发交易周期。
- 新增 `scheduler_leases`：跨进程原子租约、运行中续租、完成后释放。
- 新增 `scheduler_cycles`：`(job_name, scheduled_for)` 数据库唯一约束，每个时间槽只能被一个实例认领。
- 新增订单唯一约束：`(strategy_id, symbol, timeframe, signal_candle_close_time, intent_type)`；竞态冲突返回既有订单。
- 新增订单来源、运行模式、测试批次、部署、调度实例、进程、工作器、容器、计划时间等溯源字段。
- acceptance 订单标记为 `operator_authorized_testnet_acceptance`，交易所补录标记为 `exchange_reconciliation`，两者不再伪装成策略绩效。
- 新增只读事故审计、调度协调报告和 24 小时加速多实例验证工具。

## 6. 验证结果

- 迁移 0001→0011 在全新 SQLite 库完整通过。
- 未授权 CLI：在网关构造前拒绝。
- API：未显式授权返回冲突错误；授权后保留原因。
- 多实例加速 24 小时：96 个十五分钟槽，96 个成功认领，0 个重复赢家。
- 真实本地引擎重启后 `/health` 返回 `status=ok`；市场心跳覆盖 BTC/ETH/SOL，数据新鲜，交易执行范围为 BTC/ETH。
- 启动后的首个状态快照 `last_auto_cycle_at=null`，证明没有“启动即交易”。
- 真实双实例竞争期间，02:40 UTC 槽仅有一个赢家，`duplicate_slot_count=0`；赢家周期 02:41:33 开始、02:42:37 完成。该周期没有新开仓，按既有 fail-closed 对账逻辑关闭了缺少保护的 Simulation 仓位。

## 7. 尚需墙钟观察的边界

加速验证证明 24 小时时间槽的唯一认领不变量，但不能替代真实 24 小时网络、交易所和进程稳定性观察。真实观察必须持续记录每个周期、心跳新鲜度、领导实例、阻断原因和外部订单来源；任何结论不得把“无订单”自动判为“调度死亡”。

真实墙钟观察已由 Codex automation 24 启动，每小时只读采样一次，共 25 次，证据写入 `artifacts/live-24h/`。该观察明确禁止调用验收、下单、撤单或平仓接口；满 24 小时后再补充最终墙钟结论。
