## 一、调度机制：谁在每隔多久触发一次交易

**触发周期**：`PAPER_RUNTIME_CYCLE_SECONDS`，默认 **300 秒（5分钟）**一次完整循环。

**两种调度实现**（由 `RUNTIME_SCHEDULER_MODE` 二选一）：

- `inprocess`（本地一键启动默认用这个）：`services/execution/scheduler.py` 里的 `RuntimeScheduler`，在 FastAPI 进程内用 asyncio 起一组周期性协程任务，除了交易循环本身，还并行跑：行情心跳（60s）、通知分发（60s）、新闻轮询（180s）、宏观日历轮询（900s）、社媒轮询（300s）、风险扫描（60s）、每日复盘检查（60s）。
- `celery`：`apps/api/celery_app.py` 用 Celery Beat 注册同样周期的周期任务，交给独立 worker 进程执行，适合多进程/生产部署。

**每次循环做什么**：遍历固定 Top20 币种列表（`services/data/universe.py::fixed_top20_assets`）+ BTC/USDT 资金费率 carry，对每个 `(paper_run, symbol)` 组合跑一次完整的"信号→风控→下单/平仓"判定，同一根已收盘K线只处理一次（用 `cycle_key` 做幂等去重，防止同一根K线被重复交易）。

## 三、① 决策判定七层漏斗（每个环节都可能导致"不开单"）

```
第1层 技术信号生成（10类）
   ↓ 一个都没有 → fail-closed "technical_signals_insufficient"
第2层 多周期确认（4h方向 vs 15m入场）
   ↓ 数据不足/方向不一致 → fail-closed "multi_timeframe_disagreement" / "confirmation_unavailable_fail_closed"
第3层 SignalEnsemble 相关性过滤 + 加权多数投票
   ↓ 打平/票数不足quorum → fail-closed "ensemble_discarded"
第4层 MetaLabel 胜率/期望收益门禁
   ↓ 样本不足 or 胜率<阈值 or 平均收益<=0 → "meta_label_bet_skipped"
第5层 LLM 二元否决
   ↓ 判定为高风险 or 调用失败(超时/无供应商/schema错误) → "llm_veto"（失败一律强制否决）
第6层 净期望值扣成本门禁
   ↓ 胜率×平均盈利 - (1-胜率)×平均亏损 - 手续费 - 滑点 <= 0 → "net_edge_after_cost_negative"
第7层 Gatekeeper 规则风控
   ↓ 无止损/敞口超限/杠杆超限/相关性超限/回撤超限/Kill Switch → 各类拒绝码
   ↓ 全部通过
生成订单 → Binance-first 网关执行 → 落地
```

代码入口：`services/execution/decision_pipeline.py::DecisionPipeline.evaluate()`（第1-6层）+ `services/execution/gatekeeper.py::ExecutionGatekeeperService`（第7层）。

**关键设计点**：第1~4层任意一层判定不通过，都会走 `_skipped()` 分支，把 `should_trade` 硬编码为 `False`。**只要 `should_trade=False`，无论 `confidence_multiplier`（信心度乘数，决定仓位大小的系数）是多少，这一次循环对这个币种就绝对不会开仓**——`services/execution/paper_runtime.py:610` 直接读取 `entry_context["paper_order_should_trade"]` 这个布尔值来决定要不要往下走开仓逻辑，`confidence_multiplier` 只在 `should_trade=True` 时才参与仓位公式计算。这一点在第五节会详细展开，因为它是判断"今天的修复到底有没有用"的关键。

### 3.1 第1层：10 类技术信号

`enabled_signals`（`services/execution/bootstrap.py` 第62-73行）：`macd` / `dow_trend`（道氏理论趋势）/ `ema_trend` / `adx` / `price_action`（含假突破识别）/ `rsi` / `vwap` / `bollinger` / `fvg`（公允价值缺口）/ `mtf_ma`（多周期均线共振）。

今天新增了一个细分设计：`direction_signals`（4h方向周期只看 `dow_trend/ema_trend/adx/mtf_ma` 这类"结构性趋势"信号）和 `entry_signals`（15m入场周期只看 `macd/price_action/rsi/vwap/bollinger/fvg` 这类"精确触发"信号），实现了此前一直缺失的"4h只判断趋势方向、15m只判断精确入场点"的职责拆分。

任何一根K线上，只要8个信号函数全部返回 `None`（没有满足条件），这一轮就直接 fail-closed，**不会用兜底逻辑伪造一个信号出来**——这是一个刻意的保守设计。

### 3.2 第2层：多周期确认

当前主力策略 `timeframe_model="4h_direction_15m_entry"`：4h判断趋势方向、15m找精确入场点、1h作为波动率/状态参考周期。确认周期重新拉取最多240根K线跑同一套信号逻辑，缺数据或方向不一致都是 fail-closed，不会因为"凑合"而放行。

### 3.3 第3层：SignalEnsemble（信号融合）

`services/strategy_library/ensemble/service.py::create_ensemble`：
1. 相关性过滤：两个信号方向一致且相关系数超过阈值时，验证分数较弱的一方权重打 25 折（不是简单减法）
2. 加权多数投票：`long_score = Σ(weight×confidence)`，`short_score` 同理，票数多的一方获胜，得到 `fused_direction` 和 `fused_confidence`
3. 2026年已从"全票一致（AND-gate）"改造为"多数票+最小法定人数（`MIN_DIRECTION_SOURCE_QUORUM=3`）"，方向票数不足法定人数或打平才 fail-closed

### 3.4 第4层：MetaLabel 下注决策（重点，直接决定开单频率）

`services/strategy_library/ensemble/service.py::create_meta_label`，核心判定公式：

```python
bet_taken = (
    len(returns) >= min_training_samples   # 默认20个样本
    and win_rate >= min_win_rate           # 主力策略今天已从0.50下调到0.42
    and average_return > min_average_return  # 默认>0
)
```

`win_rate`/`average_return` 的数据来源有两种：
- **默认（当前实际生效）**：最近约47根K线里、沿着当前融合方向的原始收益率序列（`_meta_label_samples`），这是一个**噪声代理**——它只统计"最近价格朝这个方向走的比例"，跟"这套信号组合历史上真实触发时到底赚不赚钱"没有直接关系
- **理想（代码已实现但当前未激活）**：`services/execution/signal_edge_stats.py::load_active_edge_stats` 会优先读取 `scripts/compute_signal_edge_stats.py` 离线生成的、基于真实历史回放（同一套止损/止盈/信号组合)的胜率统计。**但仓库里目前没有 `artifacts/signal_edge_stats/` 目录**，说明这个"真实统计"从未被生成过，系统事实上一直在用噪声代理做生死判定

`bet_taken=False` 时 → `_skipped(reason="meta_label_bet_skipped")` → `should_trade=False`，直接不开单。

### 3.5 第5层：LLM 二元否决（⚠️ 本报告重点排查对象之一）

`services/agents/llm_runtime.py` 用三路 LLM 做 fallback：Anthropic Claude（付费，已配置key但未指定为veto agent）→ OpenRouter 免费模型 → GitHub Models 免费模型。Prompt 严格限定 LLM 只能输出 `{"veto": bool, "veto_reason": str}`，不允许建议方向/价格/仓位。

**Fail-closed 设计**（`services/agents/service.py::_execute_llm_veto`）：
```python
except TimeoutError:      veto = True   # "llm timeout -> fail closed"
except RuntimeError:      veto = True   # "llm runtime not configured or unavailable -> fail closed"
except Exception:         veto = True   # "schema validation failed -> fail closed"
```
**只要三路 LLM 全部不可用，这一次循环就会被强制否决，且这个否决对每一个候选订单、每一次循环都生效，不是偶发的**。当前已知：OpenRouter 免费模型返回 HTTP 429（限流耗尽），GitHub Models token 返回 401（权限范围不足），Claude 虽配了 key 但 `AGENT_LLM_PROVIDER_MAP` 没有把它指定为 veto agent 的默认路由。这意味着**当前很可能三路全灭，等价于"否决器永远说不"**。

`should_trade = not (veto_result is not None and veto_result.veto)`，一旦 veto=True，`should_trade=False`，同样不开单。

### 3.6 第6层：净期望值扣成本门禁

`services/execution/net_edge.py::net_edge_rejection_codes`，只在 `should_trade` 已经为真、进入 Gatekeeper 前才会追加检查：

```python
edge = win_rate*average_win - (1-win_rate)*average_loss - round_trip_fee_rate - round_trip_slippage_rate
if edge <= 0: reject("net_edge_after_cost_negative")
```

这里用的 `win_rate/average_win/average_loss` 与第4层 MetaLabel 是**同一套统计数据源**（同样默认走47根K线噪声代理），手续费/滑点今天已经从"两三倍高估"调整为贴近 Binance USDM 真实费率（5bps taker）。

### 3.7 第7层：Gatekeeper 规则风控

`services/execution/gatekeeper.py`：Kill Switch、开仓必须有止损、单品种/组合总敞口、持仓数量、杠杆、日/周亏损、回撤、连续亏损（Martingale检测）、跨品种相关性簇敞口（同方向相关系数>0.70的对手仓位≥2个即拒绝）、净方向敞口。这一层是纯规则判定，不依赖LLM，出问题概率最低。

## 四、仓位大小怎么算的（第7层通过之后）

`services/execution/paper_signal.py` 真实公式：

```python
risk_budget = account_equity * risk_per_trade          # 主力策略今天已调到 5%（此前1.5%）
quantity = risk_budget / abs(reference_price - stoploss_price)
volatility_sized_notional = quantity * reference_price
requested_notional = min(
    volatility_sized_notional,
    account_equity * max_position_fraction              # 今天已调到 35%（此前18%）
) * confidence_multiplier
```

止损距离计算优先级：`fixed_bps` > `basis_bps` > `atr_multiple × ATR` > `max_net_loss_bps` > 默认1.5%。

止盈：固定 2R 全平（今天保留这个配置，因为仓库自己的历史回放对比证明 ExitLadder 阶梯止盈净期望值为负）。

平仓优先级（同一根K线内）：保护性止损/止盈（含移动止损棘轮收紧） > 反向信号平仓 > 时间止损。移动止损只会收紧、不会放松，且只在浮盈达到 `trail_after_r × 初始止损距离` 后才启动。

## 六、一图总览：现在系统的真实脾气

- 它**不是"看到机会就随便开"的系统**，而是一个层层设卡、默认保守（多处 fail-closed）的系统，这是刻意的风控设计，不是bug
- 但正因为层层设卡，**任何一层的供应商/数据缺陷都会导致"整体看起来像没有信号"**，而日志/数据库里其实清楚记录了具体在哪一层被拒——只是目前没有一个前端面板把这个漏斗通过率可视化出来，导致排查必须靠人工查库
- 想要"让它更愿意开单"，正确姿势是：**先搞清楚当前主要卡在漏斗第几层（用第七节的诊断脚本查 `decision_snapshots` 的拒绝原因分布)，再针对性地调那一层**，而不是像今天这样，同时调整仓位大小、胜率阈值、手续费假设等多个不一定是瓶颈的参数
