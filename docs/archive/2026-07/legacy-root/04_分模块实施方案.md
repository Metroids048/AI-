# 自动开平仓/量化策略问题 — 分模块实施方案（给 Claude Code 执行用）

> 依据：上一份《全项目审查与自动开平仓问题根因诊断报告》。这份文档只讲"怎么改"，每个模块都给了
> 具体文件路径、函数签名、改动方式和验收标准，可以按顺序一个个丢给 Claude Code 去做，做完一个验收一个再进下一个，
> **不要一次性把全部模块打包成一个大 PR**——之前几轮"改了一版也无事发生"的部分原因就是改动批次太大、
> 出问题之后不好定位是哪一处改动导致的。

## 总体顺序（有依赖关系，不能跳着做）

```
模块0 运行时对齐核查工具  ← 必须最先做，且每次改完代码都要重新跑一遍
模块1 仓位计算诊断日志
模块2 链路验证单隔离       ← 1、2 互相独立，可以并行
模块3 相关性风控阈值可配置化
模块4 Top20 数据完整性巡检 ← 3、4 互相独立，可以并行
模块5 真实边际统计流水线化 ← 依赖模块0（要确保跑出来的统计是基于当前真配置）
模块6 缠论买卖点信号        ← 独立分支，随时可以单独推进，不依赖其他模块
模块7 分批止盈 A/B 测试框架通用化
模块8 失败知识回流（P2，可选）
模块9 Agent 执行器补齐（P2，可选，为将来参数寻优做准备）
```

## 模块0：运行时对齐核查工具

**目标**：把"当前跑着的进程读到的配置，和代码仓库里最新的配置是否一致"这件事，从人工排查变成一条命令就能核实，
彻底解决"改了一版也无事发生"这个反复出现的问题。

**新增文件**：`scripts/verify_runtime_config_sync.py`

**具体逻辑**：
1. 从命令行参数或 `POSTGRES_URL` 环境变量连接当前运行时实际使用的数据库（不是新建一个）。
2. 查询 `strategies` 表里 `strategy_key = 'auto_paper_mature_templates'`（即 `AUTO_PAPER_TECHNICAL_KEY`）那一行的
   `rules` JSON 字段，解析出 `position_rules`/`takeprofit_rules`/`entry_rules` 三段。
3. 同时 `from services.execution.bootstrap import AUTO_PAPER_TECHNICAL_RULES` 直接导入代码里当前的期望值。
4. 逐字段 diff 这两份 dict（`risk_per_trade`、`max_leverage`、`max_position_fraction`、`min_notional_usdt`、
   `takeprofit_rules`、`meta_label_min_win_rate`、`core_fee_bps`/`standard_fee_bps` 等），**只要有一个字段不一致，
   就打印出具体字段名 + 数据库里的值 + 代码里的值，并以非零退出码退出**。
5. 额外核查一项：查当前进程实际连接的 `POSTGRES_URL`（可以通过一个已有的、会做真实数据库查询的 API，比如
   `GET /api/v1/execution/paper-runs/{id}/decision-trace`，判断它是否返回 200 而不是 500/超时——如果 500，
   直接提示"当前 API 进程连接的数据库不可达，很可能是用了错误的 POSTGRES_URL 启动的，参考
   `.github/agent/memory/task-history.md` TASK-059 里记录的同类故障"）。

**使用方式**：每次改完 `bootstrap.py`/`risk_tiers.py` 里的参数、重启服务之后，第一件事就跑
`python scripts/verify_runtime_config_sync.py`，green 了才算这次改动真正生效，不 green 就先去查进程有没有真重启，
而不是继续怀疑代码逻辑本身。

**验收标准**：故意把 `bootstrap.py` 里 `risk_per_trade` 改成一个不同的值但不重启数据库里已有的策略记录，
脚本必须能检测出差异并报错退出；重启标准启动脚本后再跑，必须变成 green。

## 模块1：仓位计算诊断日志（把"为什么这单只有0.04%"从猜测变成读日志就知道）

**涉及文件**：`services/execution/paper_signal.py`

**具体改动**：

1. 在 `_requested_notional()` 里，把中间计算过程的关键变量收集进一个 dict，并作为日志/trace 输出，而不是只返回最终一个 float：

```python
# services/execution/paper_signal.py
import logging
logger = logging.getLogger(__name__)

MIN_SANE_NOTIONAL_FRACTION = 0.005  # 低于账户权益 0.5% 时打警告日志

@staticmethod
def _requested_notional(*, strategy, paper_run, symbol, requested_leverage,
                         confidence_multiplier=1.0, reference_price=None, stoploss_price=None):
    ...
    # 在 return base * max(confidence_multiplier, 0.0) 之前插入：
    final_notional = base * max(confidence_multiplier, 0.0)
    if account_equity > 0 and final_notional / account_equity < MIN_SANE_NOTIONAL_FRACTION:
        logger.warning(
            "sizing_sentinel_triggered symbol=%s account_equity=%.2f risk_budget=%.2f "
            "volatility_sized_notional=%.2f max_fraction_cap=%.2f confidence_multiplier=%.4f "
            "final_notional=%.4f final_fraction=%.6f",
            symbol, account_equity, risk_budget, volatility_sized_notional,
            account_equity * max_fraction, confidence_multiplier,
            final_notional, final_notional / account_equity,
        )
    return final_notional
```

2. `_build_risk_state()` 里同样对 `correlation_risk_discount` 做一次日志：折扣被触发时（`high_correlation_peer_count > 0`）
   打印 `symbol`、`max_peer_correlation`、`correlation_risk_discount`、折扣前后的 notional。

3. 把这条 WARNING 日志的 `logger` name（比如 `services.execution.paper_signal.sizing_sentinel`）单独配置一个
   可以快速 grep 的前缀，方便你直接 `grep sizing_sentinel_triggered` 日志文件。

**验收标准**：新增单测 `tests/services/test_paper_signal.py::test_sizing_sentinel_logs_when_notional_below_threshold`，
构造一个 confidence_multiplier 很低（比如 0.05）的场景，断言日志里出现了 `sizing_sentinel_triggered` 且包含所有中间变量字段。
再跑一次线上真实数据（用模块0的核查工具确认进程是最新代码后），观察日志里是否真的出现过这条 WARNING——
如果从没出现过，说明 0.04% 这类订单本来就不是当前代码算出来的，直接印证了诊断报告里"大概率是旧进程/旧配置"的结论。

## 模块2：链路验证单与策略表现单隔离

**目标**：给你一种"专门用来测试下单/止损/止盈/平仓链路本身有没有问题"的模式，产生的订单**不会**混进策略表现统计，
也不会因为 `net_edge_after_cost_negative` 被拒绝（因为这类单子的目的就是测试链路，不是测试盈利能力）。

**涉及文件**：`services/execution/bootstrap.py`、`apps/api/routers/runs.py`

**具体改动**：

1. 仿照已有的 `OPERATOR_EXPERIENCE_STRATEGY_KEY` / `bootstrap_operator_experience_strategy()` 模式
   （`services/execution/bootstrap.py:118-123` 附近），新增：

```python
LINK_VERIFICATION_STRATEGY_KEY = "link_verification_fixed_notional"

LINK_VERIFICATION_RULES: dict[str, Any] = {
    "entry_rules": {
        "technical_pipeline": True,
        "timeframe_model": "4h_direction_15m_entry",
        "direction_timeframe": "4h",
        "entry_timeframe": "15m",
        "enabled_signals": ["macd", "dow_trend", "ema_trend", "adx", "price_action", "rsi", "vwap", "bollinger"],
        "meta_label_min_win_rate": 0.0,       # 关掉二级过滤，只为验证链路能不能走通
        "min_estimated_net_edge_bps": -100000, # 关掉成本门禁，同样只为验证链路
        "default_enabled_for_auto_trading": False,  # 必须手动触发，绝不进 7x24 自动调度
    },
    "exit_rules": {"close_on_opposite_signal": True, "time_exit_hours": 24, "time_exit_min_r": 0.5},
    "stoploss_rules": {"atr_multiple": 2.0, "fixed_bps": 250},
    "takeprofit_rules": {"risk_reward": 2.0},
    "position_rules": {
        "notional_usdt": 100,   # 固定金额，不用 risk_per_trade 动态计算，方便你验证"这单该收到的钱是不是100"
    },
}

def bootstrap_link_verification_strategy() -> str | None:
    """独立 PaperRun，仅用于验证下单/止损/止盈/平仓链路，永不参与策略表现评估，永不自动调度。"""
    risk_profile_id = bootstrap_medium_risk_profile()
    return _ensure_auto_paper_run(
        runtime_key="link_verification",
        strategy_key=LINK_VERIFICATION_STRATEGY_KEY,
        strategy_lane="link_verification",
        core_thesis="Fixed-notional order-lifecycle verification only; not a performance signal.",
        rules=LINK_VERIFICATION_RULES,
        risk_profile_id=risk_profile_id,
    )
```

2. **不要**把这个函数加进 `bootstrap_local_paper_runtime()`（那样会导致它每次启动都自动创建），改成一个显式的
   API 端点，你想测的时候手动触发一次：在 `apps/api/routers/runs.py` 新增
   `POST /api/v1/execution/link-verification/bootstrap`，内部调用 `bootstrap_link_verification_strategy()`
   返回 `paper_run_id`，之后你对这个 `paper_run_id` 手动调用已有的 `/paper-runs/{id}/auto-cycle` 或 `/step` 接口。

3. 任何统计/报表类查询（比如复盘报告、Review Agent 聚合）如果是按 `strategy_lane` 或 `auto_paper_runtime_key`
   过滤的，确认 `link_verification` 不会被包含进"策略表现"类的聚合里——检查
   `services/review/service.py` 里聚合查询是否需要显式排除这个 lane（如果它现在是按全部 PaperRun 不加区分地聚合，
   这里需要加一行过滤）。

**验收标准**：新增 `tests/api/test_paper_runtime_api.py::test_link_verification_lane_produces_orders_and_is_excluded_from_review`，
断言：(a) 这条 lane 能在 `net_edge_after_cost` 明显不达标的情况下依然产生 `filled` 订单（因为门禁被关掉了）；
(b) Review 聚合报告的策略表现指标不包含这条 lane 产生的订单。

## 模块3：组合相关性风控阈值可配置化

**目标**：把现在硬编码在两个文件里的 `0.70`/`2`/`0.35`/`0.40` 变成可调参数，这样你可以自己决定
"要不要放宽相关性风控去测试Top20各币独立表现"，而不需要改代码。

**涉及文件**：`shared/models/workflow.py`（`AutoTradingSettings`）、`services/execution/paper_signal.py`、
`services/execution/gatekeeper.py`、`apps/api/routers/runs.py`（`update_paper_run_auto_settings`）

**具体改动**：

1. `AutoTradingSettings`（`shared/models/workflow.py:134-167`）新增四个字段，默认值等于当前硬编码值（改动前后行为不变）：

```python
correlation_peer_threshold: float = Field(default=0.70, ge=0, le=1)
correlated_peer_count_limit: int = Field(default=2, ge=1, le=20)
correlated_cluster_exposure_limit: float = Field(default=0.35, ge=0, le=1)
net_directional_exposure_limit: float = Field(default=0.40, ge=0, le=1)
```

2. `update_paper_run_auto_settings`（`apps/api/routers/runs.py`）把这四个字段一并写入
   `paper_run.execution_profile`（跟现有的 `max_leverage`/`daily_loss_limit` 等字段完全同样的写入方式，
   照抄那几行即可）。

3. `paper_signal.py::_build_risk_state()` 签名新增读取（从 `paper_run.execution_profile` 取，取不到再退回当前硬编码值，
   保证向后兼容）：

```python
correlation_threshold = float(paper_run.execution_profile.get("correlation_peer_threshold", 0.70))
...
if coefficient > correlation_threshold and position.side == direction:
    ...
if high_correlation_peer_count > 0 and max_peer_correlation > correlation_threshold:
    correlation_risk_discount = max(0.5, 1.0 - max_peer_correlation)
```

4. `gatekeeper.py::_evaluate_numeric_risk()` 同样把 `risk_state` 上新增的四个阈值字段（需要在
   `ExecutionRiskState` 模型里新增对应字段并由 `_build_risk_state` 填入，而不是从 `profile: RiskProfile` 读——
   因为当前这条链路里 `RiskProfile` 对象本身没有传到这一层，走 `execution_profile` 这条现成通路成本最低）：

```python
peer_count_limit = risk_state.correlated_peer_count_limit  # 新增字段，_build_risk_state 里从 execution_profile 读入并塞进 ExecutionRiskState
cluster_limit = risk_state.correlated_cluster_exposure_limit
net_limit = risk_state.net_directional_exposure_limit
...
elif risk_state.high_correlation_peer_count >= peer_count_limit:
    rejection_reasons.append("correlated_exposure_limit_exceeded")
elif risk_state.correlated_cluster_exposure + requested_fraction > cluster_limit:
    rejection_reasons.append("correlated_cluster_exposure_exceeded")
if abs(risk_state.net_directional_exposure + requested_signed_fraction) > net_limit:
    rejection_reasons.append("net_directional_exposure_exceeded")
```

5. 前端 `RuntimePanels.jsx` 的 `AutoSettingsPanel` 加四个对应的数值输入框（可以先跳过，不影响后端生效，
   前端可以晚一点再补）。

**验收标准**：新增/改写 `tests/services/test_execution_gatekeeper.py` 里已有的相关性测试，参数化跑一次默认阈值
（应与改动前行为完全一致）和一次自定义阈值（比如把 `correlated_peer_count_limit` 调到 5，验证原本会被拒的
第2/3个高相关订单现在能通过）。

## 模块4：Top20 数据完整性巡检

**目标**：确认"某些山寨币从来不开单"里，有多少是因为 60 根K线数据不完整导致 `portfolio_correlation_unavailable`，
把这个从假设变成实测数字。

**新增文件**：`scripts/audit_symbol_data_completeness.py`

**具体逻辑**：
1. 遍历 `DEFAULT_BINANCE_TOP20` 全部20个币。
2. 对每个币，调用 `data_repo.list_ohlcv_bars(symbol=symbol, timeframe="1h", limit=61)`（跟
   `paper_signal.py::_build_risk_state` 里用的一模一样的查询），记录实际拿到多少根、最早/最晚时间戳、
   有没有明显的时间缺口（相邻两根间隔超过预期的1小时太多）。
3. 输出一张表：币种 / 实际根数 / 是否≥61 / 最新数据距现在多久。
4. 同时统计过去7天内该币种在 `decision-trace` 的 `last_cycle_decisions`（如果有持久化的历史，或者从
   `OrderExecution`/`FailureRecord` 表里查）中出现 `portfolio_correlation_unavailable`、
   `technical_signals_insufficient`、`confirmation_unavailable_fail_closed` 这几种拒绝原因的次数占比。

**验收标准**：跑完输出一份 CSV/Markdown 表格，直接可以回答"Top20 里有几个币是因为数据不全从来没资格开单"这个问题——
如果确实有该现象，下一步是去修 `services/data` 里对应币种的行情采集/回填逻辑（哪个币种缺数据就单独排查那个采集任务），
而不是继续调风控阈值。

## 模块5：真实边际统计流水线化

**目标**：把 `scripts/compute_signal_edge_stats.py` 从"手动跑一次"变成"定期自动刷新"，让
`net_edge_after_cost` 门禁始终用真实历史统计而不是噪音代理指标，同时你能持续观察"这套策略离真正覆盖成本还差多少"，
而不是只在某一天手动跑一次看一眼。

**涉及文件**：`services/execution/tasks.py`、`apps/api/celery_app.py`

**具体改动**：

1. 把 `scripts/compute_signal_edge_stats.py::main()` 里的核心逻辑抽出一个可被 Celery task 直接调用的函数
   （现在是纯 CLI 脚本，需要拆出一个不依赖 `argparse`/`sys.exit` 的 `compute_and_write_edge_stats(strategy_key, days, min_trade_samples, max_age_days)` 函数，`main()` 里调这个函数再包一层参数解析/退出码）。
2. `services/execution/tasks.py` 新增 `refresh_signal_edge_stats` Celery task，调用上面这个函数，
   固定跑 `AUTO_PAPER_TECHNICAL_KEY`（以后有其他策略要接入这套真实边际统计，往列表里加就行）。
3. `apps/api/celery_app.py` 的 `beat_schedule` 里，仿照已有的 `volatility-asset-risk-tiers-weekly`，加一条：

```python
"signal-edge-stats-weekly": {
    "task": "services.execution.tasks.refresh_signal_edge_stats",
    "schedule": crontab(hour=4, minute=0, day_of_week="sun"),
},
```

4. 每次刷新后的结果（`win_rate`/`average_win`/`average_loss`/`sample_count`）除了写 artifact 文件，
   也发一条通知到你已有的 Notification Outbox（`services/notifications.py`），这样你不用主动去看文件，
   每周会自动收到一条"当前策略真实历史胜率/盈亏比是多少，离盈利门槛还差多少"的推送——这一步是直接
   针对你"已经改了太多版但不知道到底有没有进展"这个感受设计的：**至少让你每周能看到一个客观数字在变好还是变坏**。

**验收标准**：本地跑一次 `refresh_signal_edge_stats` task，确认 `artifacts/signal_edge_stats/auto_paper_mature_templates/active.json`
被更新，且时间戳/样本数正确；确认 Notification Outbox 里出现了对应的通知记录。

## 模块6：缠论买卖点信号（你独有的边际来源）

这一块不建议直接让 Claude Code "实现缠论"，因为缠论本身有多个流派、算法定义有分歧，直接生成代码大概率
做出一套你不认可的判定标准。建议按下面这个顺序拆成可以分别验收的小任务：

1. **第一步（你来做，不是 Claude Code）**：找 20~30 段你自己历史上判断得比较有把握的一买/二买/三买（或对应的卖点）
   K线区间，记录"币种 + 时间范围 + 你认为的买卖点类型 + 具体K线时间戳"，整理成一个简单的 CSV。这一步是必须人工做的，
   因为这是"你认可的标准"本身的定义，代码没法替你决定。
2. **第二步（Claude Code 做）**：新增 `services/strategy_library/technical/chan_theory.py`，先只实现最基础、
   争议最小的两层：顶底分型（fractal）识别 + 笔（bi）的合并规则（用你在第一步整理出的标注反推参数，
   比如"至少间隔多少根K线才算独立的顶/底分型"）。**先不要做线段、中枢、背驰**，这几层在业界分歧更大，
   等分型+笔这一层的输出和你的人工标注吻合度过关了再往上加。
3. **第三步（Claude Code 做）**：新增 `scripts/backtest_chan_signal_against_labels.py`，把第二步的输出和
   第一步的人工标注做重合度对比（时间窗口内是否命中、方向是否一致），输出一个吻合度百分比。
   **这一步的验收标准由你自己定**——你觉得吻合度到多少算"可以接入"，这是你的判断，不是代码能替你决定的。
4. **第四步**：吻合度过关后，仿照现有8个信号的写法（比如 `services/strategy_library/technical/macd.py` 的结构），
   实现 `generate_chan_theory_signal()`，返回标准 `TradeSignal`，加进 `bootstrap.py::AUTO_PAPER_TECHNICAL_RULES`
   的 `enabled_signals` 列表——**不需要改 `decision_pipeline.py` 主链路代码**，因为信号分发已经是白名单机制
   （`decision_pipeline.py:266-294`），新增信号只需要在分发表里加一行映射。

## 模块7：分批止盈 A/B 测试框架通用化

**目标**：现在"ExitLadder 不如固定2R"这个结论，是靠一次性脚本跑出来、写死在审计文档里的
（`docs/audits/2026-07-12-exitladder-replay-comparison.md`）。如果你想重新设计一版分批止盈规则再测，
现在没有一个可以重复调用的通用对比工具，每次都要重新写一次性脚本。

**涉及文件**：`services/validation/technical_replay.py`（已有的历史重放引擎）

**具体改动**：
1. 把 "ExitLadder vs 固定2R" 这次对比背后复用的重放引擎，抽出一个通用函数
   `compare_exit_policies(entry_config, exit_policy_a, exit_policy_b, symbols, date_range) -> ComparisonReport`，
