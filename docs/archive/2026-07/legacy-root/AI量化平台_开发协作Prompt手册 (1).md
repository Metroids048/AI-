# 开发协作 Prompt 手册

> 使用说明:本手册分两部分。**第一部分是通用核查 Prompt**,与具体项目无关,以后不管接手什么
> 项目、什么技术栈,用 Codex / Claude Code 开始工作前都先跑一遍这个,建立"不轻信文档、只信
> 实际验证结果"的工作方式。**第二部分是 AI Quant Research Platform 这个项目专属的分阶段
> 开发 Prompt**,换了项目就不适用,需要重新按同样的方法论生成一套新的。

---

# 第一部分:通用核查 Prompt(适用于任何项目,与技术栈无关)

## 〇、通用「先核验、再开发」Prompt(每接手一个新项目/新会话时先用这个)

这一版不假设任何具体的目录结构、文件名、编程语言或架构模式——所有这些都要求 agent
自己先探测清楚,而不是我在 prompt 里帮它写死。

```
你正在接手一个已经存在的代码仓库,不是从零开始。这个仓库可能有大量前期文档、部分
已实现的代码、部分只是骨架或占位符的代码。在做任何修改之前,你必须先完成一次完整的
现状核验,不能读了文档就当作真实状态,也不能只抽样看几个文件就下结论。

【第一步:探测项目结构和技术栈,不要假设】
1. 先看整个目录树(排除 .git、依赖锁目录、构建产物目录),识别:
   - 这是什么语言/技术栈(通过 package.json / pyproject.toml / go.mod / Cargo.toml /
     pom.xml / *.csproj 等配置文件判断,不要凭经验猜)
   - 测试框架是什么、怎么运行(pytest / jest / go test / cargo test / mvn test 等,
     从配置文件或 CI 配置里找到真实命令,而不是套用你熟悉的默认命令)
   - 是否有 CI 配置(.github/workflows、.gitlab-ci.yml 等),如果有,记录它实际执行
     哪些检查
   - 是否存在任何"给AI/协作者看的说明文件",常见命名包括但不限于:
     README、AGENTS.md、CLAUDE.md、CONTRIBUTING.md、docs/ 目录、ARCHITECTURE.md、
     ADR(架构决策记录)目录等——找到所有这类文件,不要只读 README 就停手
   - 是否存在任何"项目状态追踪"类文件,例如状态矩阵、路线图、TODO列表、
     issue backlog 的本地镜像等

2. 阅读你找到的所有说明性文档,梳理出:
   - 这个项目声称的整体架构/分层原则是什么
   - 有没有明确写出的、不允许违反的硬性规则(例如某些模块之间禁止直接依赖、
     某些外部服务只能通过特定方式调用、某些决策已经被裁定不再讨论)
   - 如果多份文档之间对同一件事的描述不一致,记录下所有冲突点,并判断:
     是否有文档里显式定义了"优先级"或"真源"关系;如果没有明确定义,
     不要自己猜哪个更权威,而是把冲突原样列出来,后面向我确认。

【第二步:核验文档声称的状态是否等于代码真实状态】
不要相信任何"已完成/已实现/done/implemented"这类描述,凡是声称已完成的部分,
都要去源码里实际打开确认:
1. 声称存在的模块/文件是否真的存在于当前的代码库里(不是被其他文件 import 但
   自身缺失;不是只在某人本地机器上存在但从未被提交)。
2. 声称"已实现"的核心逻辑,是否是真实计算/真实调用,还是硬编码的占位返回值、
   写死的常量、直接 return 固定结果的桩代码(stub)。
3. 声称"已通过测试"的部分,对应测试是否真的验证了业务正确性,还是只验证了
   "调用不报错""对象能被创建"这种弱断言,不足以证明逻辑本身是对的。
4. 实际执行以下类型的检查,把结果当作唯一可信依据:
   - `git log --oneline --all` 和 `git status`,了解真实提交历史和当前工作区状态
   - 用该项目实际使用的测试命令完整跑一遍全部测试,记录所有失败/报错/跳过
   - 搜索代码里的 TODO / FIXME / stub / placeholder / 占位 / mock 等关键词,
     列出所有命中位置
   - 检查 .gitignore(或等价的忽略规则文件)是否有过于宽泛、可能意外排除了
     真实源码目录的规则(常见问题:忽略规则没有用路径锚定符号,导致匹配到
     不该匹配的同名子目录)
   - 如果有 CI,尝试确认最近几次运行是否真的通过,而不是假设"配了CI=在正常运行"

【第三步:输出现状核验报告,不要跳过这一步直接开始开发】
按下面的结构输出:
- 项目技术栈与结构摘要
- 文档体系摘要(有哪些说明文档,各自定位是什么)
- 文档间的冲突点清单(如果有)
- 「文档声称状态」 vs 「代码实际状态」对照表,每一条不一致都要给出具体文件路径
  和代码片段作为证据,不能只写结论不给证据
- 你认为当前最需要优先处理的问题清单(按风险/阻塞程度排序,而不是按实现难易排序)

【第四步:开发阶段的行为准则】
1. 严格遵循第一步里梳理出的既有架构原则和硬性规则,不允许为了图方便而绕开、
   也不允许在没有明确授权的情况下引入新的架构模式、新的依赖库或新的设计范式。
   如果你认为现有架构有问题,先提出来讨论,不要边开发边悄悄改架构。
2. 新增/修改代码前,先确认相关的数据结构/接口契约是否已经在项目里定义过;
   如果已有定义,复用它,不要另起一套平行的、语义重复的结构。
3. 每完成一个任务,必须:
   a. 用项目实际的测试命令重新跑一遍测试,确认没有引入新的失败
   b. 如果项目里存在状态追踪类文档(状态矩阵/路线图/CHANGELOG等),据实更新,
      不要写"已完成"除非你真的验证过;如果项目里没有这类文档,建议询问我是否
      需要新建一个,而不是自作主张创建一套新的追踪体系
   c. 如果项目有决策记录类文件,把本次任务中做出的关键判断记录进去
4. 一旦发现任务范围与已有文档/既有实现冲突,或者发现某个"已完成"的标注其实
   是假的,立刻停下来报告,不要为了完成任务而绕过冲突或在错误的基础上继续叠加。

【第五步:诚实汇报,不确定就说不确定】
- 汇报时给出可验证的证据(命令的真实输出、具体文件路径和行号),不要用
  "应该没问题""大概率通过"这类模糊表述替代实际验证。
- 不确定的地方明确标注"未验证/不确定",不要为了让汇报看起来完整而编造结论。

现在,请先完成【第一步】和【第二步】的探测与核验,输出【第三步】的现状核验报告,
然后停下来等待我确认后再进入【第四步】的开发。
```

**这个 Prompt 的通用性体现在**:它不写死任何具体文件名、语言、架构风格,而是要求 agent
自己去发现这些信息;它的核心约束是行为层面的("先核验再开发""声称完成必须有证据""发现
冲突要停下来问",而不是"这个项目必须用六层架构")。换到任何项目都可以直接整段复制使用。

# 第二部分:AI Quant Research Platform 专属分阶段开发 Prompt

> 下面这些是把「第一部分」的通用方法论,应用到这个具体项目后得到的结果——也就是说,
> 这些 Prompt 本身是第一部分核验流程跑完之后的产物,换了项目不能直接套用,需要重新

## 一、Phase 1a — 地基修复(最高优先级,必须先做)

**目标**:让全新 clone 的仓库能跑绿 `pytest`,消除文档与代码的既有偏差。

```
任务:修复仓库的地基问题,不新增任何业务功能。

背景:经排查,.gitignore 中的 `data/` 规则(未加前导斜杠锚定)导致 Git 把
services/data/ 整个目录当成"任何路径下名为 data 的目录"排除在外,从未被提交。
但 services/validation、services/execution、apps/api/routers、以及多个测试文件
都在 import services.data,导致全新 clone 后 `pytest -q` 直接因
ModuleNotFoundError 崩溃 6 个测试模块。

请完成:
1. 检查本地工作区(不只是这个 clone)是否存在 services/data/ 的真实源码文件
   (repository.py、binance.py 等),如果存在,确认内容完整性。
2. 修正 .gitignore:把 `data/` 改为更精确的规则(例如只忽略仓库根目录下的
   `/data/` 运行时产物目录,不要影响 services/ 下的同名子目录),并审查
   .gitignore 里其他没有前导斜杠的规则是否有类似的误伤风险(比如 `artifacts/`、
   `coverage/` 是否也可能匹配到非预期路径)。
3. 把 services/data/ 正确加入版本控制并提交。
4. 清理已经被误提交的运行时产物,例如根目录下的 .pytest_ai_quant.db 二进制文件,
   加入 .gitignore 并从 git 历史的当前分支中移除跟踪(不需要改写历史,只需要
   `git rm --cached` 后续不再提交)。
5. 解决 `pip install -e ".[dev]"` 报出的 ResolutionImpossible 依赖冲突
   (定位是 langchain/llama-index 与其他依赖的版本冲突),给出修复后的
   pyproject.toml,并说明你的版本选择理由。
6. 修复后完整跑一遍 `pytest -q`,把全部输出贴出来,确保 0 failed / 0 error。
7. 检查 GitHub Actions 的 CI 运行记录(如果无法直接访问,则在报告里提醒我
   去 Actions 标签页确认最近几次运行是否为绿色),如果 CI 一直是红的却没人
   处理,在 decisions-log.md 里记一条,并给出后续避免这种情况的建议
   (例如给仓库加一个 status badge 到 README)。
8. 更新 implementation-status-matrix.md,把 services/data 相关行的
   "落地证据"列改成实际验证过的状态,不要照抄旧描述。

完成后输出一份修复报告,附带 pytest 完整输出和你对 .gitignore 规则改动的说明。
```

## 二、Phase 1b — 回测引擎去水分(把硬编码指标换成真计算)

```
任务:修复 services/validation/carry.py 中被硬编码的核心指标,使其成为真实计算。

现状问题(已核实):
- sharpe = 1.35 if total_trades and expectancy > 0 else 0.0  # 硬编码
- max_drawdown = 0.08 if total_trades else 1.0                # 硬编码
- cost_bps = 14 / 10000 是固定常数,不是基于订单簿深度的滑点估算

请按照 docs/architecture/validation-methodology.md 的方法论要求实现:
1. Sharpe:基于真实的交易收益序列计算年化夏普比率(需要明确调仓频率对应的
   年化系数,并在代码注释里写清楚假设)。
2. 最大回撤:基于逐笔交易构建的权益曲线(equity curve)真实计算,而不是常数。
3. Deflated Sharpe Ratio:实现 BacktestReport.trials_count 和
   BacktestReport.deflated_sharpe 字段的真实计算逻辑,校正因为在同一批
   alpha/策略库上反复搜索组合带来的多重检验偏差(可先实现 Bailey & López de
   Prado 的经典 DSR 公式,给出参考文献注释)。
4. 成本模型:至少先用"历史滑点统计"或"基于价差的保守估算"替代固定 14bp,
   并在 BacktestReport.total_cost_bps 中体现手续费/滑点/资金费率三项的
   分项数值,而不是合并成一个数。
5. 补充/更新单元测试:测试用例必须能够检测出"指标被写死"这种问题,
   例如构造两组不同盈亏分布的交易序列,断言算出的 Sharpe/MaxDD 确实不同
   (现有测试只断言 total_trades >= 1,不足以发现硬编码问题,需要加强)。
6. 完成后跑 pytest,并在 implementation-status-matrix.md 里如实更新
   carry backtest 这一行的状态说明,明确指出"指标已从占位符改为真实计算"。

如果 Deflated Sharpe 或滑点估算的具体公式在文档里没有给出足够细节,
先提出你打算采用的具体公式和理由,等我确认后再写代码,不要自行假设。
```

## 三、Phase 1c — WorldQuant Alpha 真实移植(优先级对齐你的第一诉求)

```
任务:把 research_source/worldquant_adapter/crypto_factor_generator.py
从"无论输入什么都输出同一条信号"的占位符,改造成真实还原 alpha 语义的实现。

现状问题(已核实):不管传入的 AlphaPlan 是什么表达式,输出永远是同一条
硬编码信号 (close.pct_change()*0.7 + volume.pct_change()*0.3)。

请完成:
1. 从我提供的本地 alpha 文件(通过 LocalAlphaScanner 已经能正确解析出
   expression/operators/inputs 结构)中,选取 10-20 条有代表性的、
   算子种类不同的 alpha 作为首批验证样本。
2. 在 research_source/worldquant_adapter/operators.py 的算子词表基础上,
   为每一类算子(至少覆盖:时序排名、滚动相关性、滚动标准差、
   横截面标准化等常见 WorldQuant 算子类别)实现对应的 pandas/numpy 计算逻辑,
   使 CryptoFactorGenerator.from_alpha_plan 真正根据 AlphaPlan.operators
   和 raw_expression 生成语义对应的可执行代码,而不是忽略输入内容。
3. 加载真实的 BTC/USDT 历史 OHLCV 数据(小规模样本即可,例如最近1年的
   1小时K线),对这批还原后的因子跑一次基础的信息系数(IC)检验,
   输出每个因子在这批数据上的 IC 均值/标准差,作为"这条移植是否至少
   在方向上说得通"的初步判断依据(不要求此时就出具正式回测报告,
   IC检验和正式回测/DSR校正是两个阶段)。
4. 把还原度不足、无法准确移植语义的算子明确标注为"暂不支持",
   在 research_source/worldquant_adapter/README.md 里列出当前支持的
   算子清单和已知限制,不要为了覆盖率而做出错误的近似实现。
5. 更新单元测试:验证不同 AlphaPlan 输入确实生成不同的信号计算逻辑
   (可以断言生成代码字符串包含与输入算子对应的关键计算调用,
   或者直接执行生成的 compute_factor 函数并断言不同输入产生不同的
   信号序列)。
6. 更新 implementation-status-matrix.md 对应行。

完成后,给出这10-20条alpha的IC检验结果摘要,以及你认为哪些算子类型
移植得比较可靠、哪些还需要人工复核。
```

## 四、Phase 1d — 多信号融合层(SignalEnsemble / MetaLabel 服务化)

```
任务:把目前只有 ORM+repository 骨架的 SignalEnsemble / MetaLabel
补上真实的服务层逻辑,并接入 API,实现"多个弱信号 -> 相关性过滤 ->
二级仓位判定"的融合链路。

请完成:
1. 实现信号相关性计算:输入一批同一时间窗口内的候选信号(可以先用
   Phase 1c 产出的alpha信号 + 手写的1-2个占位技术信号做联调),
   计算两两相关性矩阵,对高度相关(设定一个可配置阈值)的信号做
   降权或剔除,只保留低相关信号进入下一步。
2. 实现一个基础版 Meta-labeling 服务:
   - 一级信号只负责产出"方向候选"(long/short/neutral + 置信度)
   - 二级模型(先用逻辑回归或简单规则即可,不要求一开始就上复杂模型)
     基于历史上同类一级信号触发后的真实盈亏结果(需要用三重界限法
     —止盈线/止损线/时间限—打标签),判断"这次要不要真的下注、
     下多大仓位"
   - 明确记录训练数据的时间范围,避免用未来数据训练当前判定逻辑
3. 把该服务接入 apps/api,补齐 SignalEnsemble/MetaLabel 相关路由的
   真实业务逻辑(目前只有 CRUD 骨架)。
4. 编写集成测试,构造一组已知盈亏结果的历史信号序列,验证 meta-label
   输出的仓位判定方向合理(至少验证:高胜率历史信号被给予更高仓位权重,
   低胜率/高相关信号被降权或过滤)。
5. 更新 implementation-status-matrix.md。

如果三重界限法的具体参数(止盈/止损/时间窗口)在现有文档里没有明确定义,
先给出你的默认参数建议及理由,等我确认。
```
