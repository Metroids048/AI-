# 量化策略库：收集 / 评分 / 淘汰机制方案

## 文档定位

本文件是开发前文档包的第 4 份，回答"策略从哪里来、怎么打分、什么时候被淘汰"这一机制设计问题。

按用户确认的范围边界：**本文件只设计收集/评分/淘汰的机制本身，不写具体策略参数**
（不包含缠论笔段的具体判定规则、道氏理论的具体摆动幅度、MACD 的具体参数取值等）。
具体策略的规则内容属于 `StrategyDraft.entry_rules` 等字段的运行期数据，由 Strategy Agent
在 Phase 1/2 实际规则化时产出，不是设计文档的内容。

本文件服从并引用：`domain-and-interfaces-design.md`（`Strategy`/`StrategyIdea`/
`SignalEnsemble`/`MetaLabel` 对象定义）、`validation-methodology.md`（评分所需的
Deflated Sharpe/压力测试/成本建模方法论）、`execution-risk-review-design.md`
（复盘结论如何反馈到策略状态）、ADR-009（WorldQuant 移植方法论而非搬运表达式）、
ADR-011（资金费率套利作为 P1 第一个落地策略）、ADR-012（信号融合归属 Strategy Layer 子模块）。

## 01 策略来源分类（收集机制）

### 1.1 六类来源（对应 AGENTS.md "策略来源，不是平台主干"原则）

| 来源类型 | `StrategyIdea.origin_type` 取值建议 | 特点 | 平台角色边界 |
|---|---|---|---|
| 人工提出 | `manual` | 研究者直接输入交易直觉/假设 | 主要来源，人工审核权重最高 |
| WorldQuant 本地 alpha 库 | `worldquant_adapter` | 方法论移植（算子+因子构造模式），非表达式搬运 | 融合层低权重投票，不作为独立策略（ADR-009） |
| GitHub 开源策略/研究项目 | `github_research` | 结构化程度不一，需要先人工/Research Agent 提炼核心逻辑 | 仅作研究灵感来源，代码不可直接搬入执行链路 |
| 学术论文 | `academic_paper` | 通常提供思路和统计证据，不提供可直接执行的规则 | 需经 Strategy Agent 规则化才能进入草案阶段 |
| 本地 A 股系统迁移 | `a_share_system_port` | 已在其他市场验证过逻辑，但需重新适配加密市场特性（永续合约/资金费率/24小时无休市） | 迁移时必须重新走完整验证链路，不可因"已在别处验证过"而降低验证门槛 |
| 新闻/社媒事件驱动灵感 | `news_social_inspired` | 由 C/D 级数据观察到的现象引发的策略假设 | 灵感来源合法，但事件数据本身仍只能作风控过滤输入，不能绕过规则化直接触发交易（呼应 ADR-013） |

新增来源类型时，只需扩展 `origin_type` 枚举，不需要新建领域对象或新的接口簇——
这是"收集"环节的机制弹性所在。

### 1.2 收集入口的统一性要求

无论来源类型是什么，所有策略灵感最终都必须先落地为 `StrategyIdea`，再经 Strategy Agent
规则化为 `StrategyDraft`，不允许任何来源类型跳过这一步直接创建 `Strategy`（呼应
domain-and-interfaces-design.md §4.2 主链路约束，以及编排约束"不允许未通过
`approve_draft` 直接进入 `create_strategy_version`"）。这保证了策略库不会因为来源不同
而产生结构不一致的"特殊策略"。

### 1.3 收集渠道的自动化程度分级

| 来源类型 | P0 | P1 |
|---|---|---|
| 人工提出 | 全量支持 | 全量支持 |
| WorldQuant 本地 alpha 库 | 接口接缝（stub） | Research Agent 自动扫描本地库，批量生成 `StrategyIdea` |
| GitHub/论文/A股系统迁移 | 不做自动扫描 | Research Agent 半自动辅助提炼（仍需人工确认） |
| 新闻/社媒事件驱动灵感 | 不适用（C/D级数据本身P0只搭框架） | 人工基于风险事件流手动提出假设，不做自动生成假设 |

## 02 评分机制

### 2.1 评分的两个层级

策略评分分两个独立层级，不能混为一谈：

1. **单策略验证评分**：一个 `Strategy`/`StrategyVersion` 在 `BacktestRun`/`PaperRun`/
   `LiveRun` 中产出的绝对表现，回答"这个策略本身好不好"。
2. **组合贡献度评分**：一个策略在加入 `SignalEnsemble` 之后，对整个信号组合的边际贡献，
   回答"这个策略值不值得留在组合里"，即使它单独表现尚可，若与已有策略高度相关也可能被淘汰。

两个层级都要打分，且第二层级的评分依赖第一层级已经产出的验证结果，不能反过来。

### 2.2 单策略验证评分：指标构成

评分不是单一数字，而是一组指标的组合判断，避免"一个好看的 Sharpe 掩盖其他问题"
（这正是外部咨询意见批评的问题）。评分依据的指标口径，全部来自
`validation-methodology.md` 已定义的方法论，本文件不重新定义指标算法，只定义
"这些指标如何组合成一个可比较、可排序的评分结构"：

| 维度 | 依据字段（`BacktestRun`/`metrics_summary`） | 在评分中的角色 |
|---|---|---|
| 风险调整收益 | Deflated Sharpe（优先于原始 Sharpe） | 主排序依据 |
| 盈利质量 | Profit Factor、Expectancy | 门槛过滤（未达标直接不进入排序） |
| 风险暴露 | Max Drawdown | 门槛过滤 + 排序惩罚项 |
| 统计显著性 | `trials_count`（测试过的参数组合数） | 对 Deflated Sharpe 的校正输入，试验次数越多，同样的原始 Sharpe 越应被打折 |
| 成本敏感度 | `total_cost_bps` | 净指标计算的分母调整；成本占收益比过高的策略即使名义达标也应降级处理 |
| 极端场景稳健性 | `stress_test_scenarios` 各场景表现 | 门槛过滤（任一场景表现远超可接受回撤即降级或拒绝，无论其他指标多好） |
| 样本外一致性 | Walk-Forward 滚动窗口的 in-sample/out-of-sample 表现差异 | 排序惩罚项，差异过大提示过拟合 |

评分结构建议为**分级制而非单一连续分数**（如 `A/B/C/D` 或 `admitted / conditional /
rejected`），理由：连续分数容易制造"精确排名"的假象，而实际上这些指标本身就带有统计噪声，
分级制更符合"达标即可进入下一阶段验证，而不是选出唯一最优策略"的产品目标（呼应
`prd.md` §1.2 产品成功标准）。

### 2.3 组合贡献度评分：相关性过滤机制

承接 `domain-and-interfaces-design.md` §3.5a `SignalEnsemble.correlation_matrix_ref`：

- 任何策略在被允许参与 `SignalEnsemble` 融合之前，必须先计算其历史信号方向序列与已在组合中
  其他策略的相关系数。
- 相关性过滤的目的不是"排除相关策略"，而是"避免同质策略重复下注同一个市场判断"——
  多个高度相关的策略同时开仓，本质上是把仓位集中度伪装成了"多策略分散"。
- 具体相关系数阈值、计算窗口长度属于 Phase 1 实现参数，不在本文件裁决（呼应
  `technical-architecture-plan.md` §13 的文档边界原则：本文件只定义"要做相关性过滤"
  这一机制，取值留给实现阶段用历史数据校准）。
- WorldQuant alpha 类来源默认权重低，且优先参与相关性过滤（因为其数量可能很大，
  更容易与其他信号产生统计意义上的伪相关），避免大量低权重同质信号稀释组合的有效信息量。

### 2.4 评分的时间维度：不是一次性判定

评分必须随着策略在验证链路中推进而持续更新，不是"回测时打一次分就定终身"：

| 阶段 | 评分更新触发 | 评分对象 |
|---|---|---|
| 历史回测完成 | `BacktestRun` 完成 | 单策略验证评分（首次） |
| 参数优化完成 | `OptimizationRun` 完成 | 单策略验证评分（更新，需重新走一遍门槛检查，不能只看优化后的单一最优参数） |
| 模拟盘运行中 | `PaperRun` 定期快照 | 单策略验证评分（实盘前的最后校验，回测评分与模拟盘评分出现显著背离本身就是一个信号） |
| 小资金实盘运行中 | `LiveRun` 定期快照 + 每日复盘 | 单策略验证评分（持续），组合贡献度评分（若已进组合） |
| 新策略加入组合 | 该新策略完成回测评分 | 组合贡献度评分（重新计算相关性矩阵，可能影响组合内已有策略的贡献度评分） |

## 03 淘汰与晋升机制

### 3.1 晋升路径（评分驱动，但人工确认，不自动执行）

评分结果驱动"建议"，不驱动"自动执行"——呼应 PRD §03 六个人工决策点硬约束。评分与状态迁移的
关系：

```
BacktestRun 评分 = admitted        -> 建议进入模拟盘（人工确认后 PaperRun 创建）
BacktestRun 评分 = conditional     -> 建议人工复核后再决定（不自动建议进入模拟盘）
BacktestRun 评分 = rejected        -> 不建议进入模拟盘，回写 FailureRecord
PaperRun 评分 = 持续达标 + 稳定期满 -> 建议进入小资金实盘（人工确认）
LiveRun 评分 = 持续达标            -> 建议继续/晋升资金规模（人工确认，资金规模决策超出本文件范围）
```

### 3.2 淘汰触发条件（机制层，不含具体数值阈值）

淘汰不是单一事件，而是以下任一类信号累积达到 Review Layer 判断标准后触发的建议
（最终淘汰仍是人工决策点）：

| 淘汰信号类别 | 触发来源 | 说明 |
|---|---|---|
| 验证不达标 | `BacktestRun.eligibility_result = rejected_with_reason` | 首轮就不达标，通常不进入组合，直接沉淀 `FailureRecord`，不算"淘汰"（因为从未被采纳） |
| 回测与模拟盘表现显著背离 | `PaperRun.paper_metrics_summary` vs `BacktestRun.metrics_summary` 对比 | 提示过拟合或市场机制已变化 |
| 持续失效模式 | Review Layer 识别到的重复性失效模式（`ReviewReport.failure_patterns`） | 例如某策略在特定 `market_regime` 下反复触发止损 |
| 组合贡献度归零或转负 | 相关性过滤后该策略对组合边际收益无正贡献，甚至因高相关性放大了组合回撤 | 即使单策略验证仍达标，也可能被从组合中移出（不等于策略被"退役"，可仅退出当前组合） |
| 风险事件关联度过高 | 该策略的执行频繁与 high severity `RiskEvent` 时间窗口重叠 | 提示策略对特定风险场景暴露过大，需要复核止损/仓位规则是否需要收紧 |
| 长期停滞 | 策略连续多个复盘周期都是"无新信号"或"持续 pause 未恢复" | 提示策略可能已不适应当前市场环境，进入待淘汰候选 |

### 3.3 淘汰不等于知识丢失

`Strategy.strategy_status -> retired` 触发时，必须保证：

- 完整的 `StrategyVersion` 历史、`BacktestRun`/`PaperRun`/`LiveRun` 记录、`FailureRecord`
  均保留可检索，不物理删除。
- `FailureRecord.recommended_change` 字段需明确写出"如果未来要复活这个策略方向，应该先改什么"，
  而不是只写"表现不好"这种无法复用的结论。
- 淘汰后的策略仍可被 Research Agent 检索到，作为"这个方向已经试过、且已知问题是什么"的
  负面知识库条目，避免未来重复踩坑（呼应 AGENTS.md Review Layer 定位："失败知识沉淀，
  供 Research/Strategy Agent 复用"）。

## 04 与信号融合/二级仓位判定的机制衔接

策略评分机制与 `SignalEnsemble`/`MetaLabel` 的关系边界（避免与 domain 文档重复裁决对象定义，
只说明评分机制如何驱动这两个对象的产生）：

- 只有评分达到"允许进入组合"门槛的策略，才会被纳入 `SignalEnsemble.strategy_refs` 候选池。
- 评分机制产出的分级结果（§2.2）不直接等同于 `MetaLabel.bet_decision`——评分回答的是
  "这个策略/组合值不值得信任"，`MetaLabel` 回答的是"这一次具体的信号要不要下注、下多大"，
  两者是不同粒度的判断，不能用同一套逻辑合并（这也是 meta-labeling 二级架构存在的意义，
  避免用一级信号的历史平均表现直接决定单次下注行为）。
- 资金费率/基差套利策略（ADR-011，P1 第一个落地策略）因其波动率无关、方向无关的特性，
  评分机制对它的适用性：门槛过滤维度基本可以直接套用（Profit Factor/Max Drawdown 等仍适用），
  但相关性过滤维度的意义较弱（它与方向性技术策略天然低相关，通常会自然通过相关性过滤），
  这属于评分机制对不同策略类型的自然适应性，不需要为它单独定义一套评分规则。

## 05 机制的可扩展性检查

本机制设计需要满足：新增一种策略来源类型、新增一种评分维度、调整淘汰阈值，都不应要求
修改领域对象结构或接口簇定义，只应要求：

- 来源类型：扩展 `StrategyIdea.origin_type` 枚举值。
- 评分维度：`BacktestRun.metrics_summary` 是一个可扩展的指标容器（已是 dict 型
  `metrics_summary`），新增指标不需要改表结构。
- 淘汰阈值：属于 Risk/Review Agent 的运行期配置参数，不属于领域模型字段，调整阈值不需要
  发版本迁移。

## 06 P0/P1 实现边界

- P0：只需要 `StrategyIdea.origin_type` 枚举定义到位（含全部 6 类来源），评分机制的
  门槛过滤逻辑文字化（已在本文件完成），不要求评分算法代码化。
- P1：评分算法实现（依赖 `validation-methodology.md` 的 Deflated Sharpe/成本建模/压力测试
  代码化）、相关性矩阵计算实现、淘汰信号的自动识别（Review Agent 具备识别 §3.2 六类淘汰信号
  的能力）。
- P2：评分机制的历史回溯分析（例如"过去一年评分体系本身是否需要调整"这种元层面复盘），
  不在本轮设计范围。
