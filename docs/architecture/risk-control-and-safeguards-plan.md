# 风控措施与保障方案

## 01 文档定位与边界

`execution-risk-review-design.md` 已经定义了风控规则族的分类清单、`RiskEvent`/
`RiskProfile` 的对象职责、Decision Veto Agent 的硬性边界（§03a）。但该文档在多处
留白了**具体取值**与**风险容忍度选择**，明确交给本文件裁决（如 §2.2a 新闻分级暂停
时长、`llm-integration-plan.md` §3.2 的超时降级选项二选一）。

本文件的职责是把这些留白填上具体数值和明确选择，**不重新定义**已确认的规则族分类、
对象字段、Agent 边界。本文件产出后，`execution-risk-review-design.md` 与
`llm-integration-plan.md` 中被引用的留白段落应视为已由本文件裁决完毕（后续如需修改
这些取值，应作为对本文件的修订，而不是绕开本文件直接改动别处）。

## 02 裁决一：LLM 否决超时降级策略

`llm-integration-plan.md` §3.2 列出的两个选项：

- 选项 A："超时即否决"
- 选项 B："超时视为无否决意见，继续走既定风控规则"

**裁决：采用选项 A（超时即否决）。**

理由：AGENTS.md 非可谈判项第 3 条"风控优先级永远高于收益"，以及本项目反复强调的
"宁可少赚不可爆仓"的定位。选项 B 的风险在于——如果 LLM 服务恰好在市场剧烈波动、
调用排队严重的时刻超时（这类时刻往往正是最需要否决层介入判断的时刻），选择"超时=
无否决意见"等于在风险最高的窗口自动放行，这与既定风控优先级原则直接冲突。选项 A
的代价是"可能错过一部分本该被放行的机会"，但这类代价是可接受的机会成本，不是
不可逆损失，与选项 B 的潜在下行损失不对称。

补充规则：

- 超时判定为否决后，仍必须完整记录 `AgentTask` 失败事件（`llm-integration-plan.md`
  §3.2 已有要求），且该记录需额外标注"超时否决"（区别于"LLM 主动否决"），便于
  Review Layer 统计超时率与主动否决率是两个不同的观测维度。
- 若同一 Agent/同一交易所在滚动窗口内超时否决次数超过阈值（具体阈值见 §05 熔断
  规则表"API 连续失败停机"一行的处理原则，超时视为一种 API 层异常信号的延伸），
  应触发对该链路的 `pause_strategy` 级别降级，而不是让"逐单超时否决"无限持续——
  持续超时本身说明 LLM 调用链路存在系统性问题，应升级为需要人工介入的风险事件，
  而不是每单都默默否决掉。

## 03 裁决二：交易所 API Key 权限要求

呼应外部顾问原始建议与 `technical-architecture-plan.md` §8.3 已登记的"必须存在的
启动期检查点"，本文件给出该检查点的具体规则：

### 3.1 硬性要求

- 用于 `paper`/`live` 环境的交易所 API Key **必须仅具备交易权限，禁止提现权限**。
  这是硬性要求，不是建议——任何交易所支持"按权限位创建 Key"的功能都应在创建时
  就关闭提现权限，而不是依赖平台事后检测来补救。
- `paper`/`live` 环境建议使用**独立子账户**，与研究/开发用途的账户物理隔离，
  避免开发过程中的任何误操作影响到有真实资金流转的账户。
- `dev`/`test` 环境不应与 `paper`/`live` 共用同一交易所账户或子账户
  （`technical-architecture-plan.md` §8.2 已确认四环境凭据物理隔离，本文件在此
  基础上补充"账户级"隔离，不只是".env 文件级"隔离）。

### 3.2 启动期自检

- 服务启动时（针对 `paper`/`live` 环境），调用交易所账户权限查询接口，确认返回的
  权限位不包含提现权限。若包含提现权限，**拒绝启动并告警**，不允许"仅告警不拒绝"
  的降级选项——因为一旦服务带着有提现权限的 Key 跑起来，风险已经存在，"事后告警"
  无法挽回。
- 该自检结果应可在界面查看（`module-feature-catalog.md` 已登记"交易所 API Key
  权限自检结果查看"为 P1 功能点），供研究者确认当前环境的 Key 权限状态，不需要
  打开代码或数据库去核实。
- 自检失败事件本身应记为 `RiskEvent`（`event_type=risk_limit_breach`，
  `severity=critical`），纳入复盘记录，即使服务因此拒绝启动，这次拒绝本身也是
  需要留痕的事件，不能只是一条控制台报错就完事。

### 3.3 `dev`/`test` 环境的例外

`dev`/`test` 环境使用的 Key 通常连接交易所测试网（testnet）或仅用于只读数据拉取，
不涉及真实资金，因此本节的强制自检**不适用于** `dev`/`test` 环境——避免在日常开发
调试时因为测试网 Key 权限模型不同而误触发拒绝启动。这个例外的边界就是"是否涉及
真实资金"，不是环境名称本身。

## 04 裁决三：RiskProfile 具体阈值

`domain-and-interfaces-design.md` §3.13 已定义 `RiskProfile` 的字段列表；当前代码中
`shared/models/risk.py` 已有 `RiskProfile` 契约，`RiskProfileRepository` 与
`/api/v1/risk/profiles` 也已落地。本文档给出的仍是 P0/P1 阶段的默认阈值建议，
作为代码化/配置化时的默认口径，而非最终锁死的数值——具体数值仍应保留为运行时可配置项
（呼应 `technical-architecture-plan.md` §08 配置管理原则），本文件的作用是给出
一组"没有更好依据时可以直接采用"的合理默认值，而不是留一个空字段让实现者随意猜。

| 字段 | 建议默认值（BTC/USDT 永续，第一阶段主市场） | 依据 |
|---|---|---|
| `single_trade_risk_limit`（单笔风险） | 账户净值的 1% | 加密永续波动率显著高于传统资产，1% 是业界常见的保守起点，避免单笔亏损对账户造成决定性影响 |
| `max_symbol_exposure`（单品种最大仓位） | 账户净值的 20% | 第一阶段仅 BTC/USDT 单一品种，该值主要防止"满仓单一品种"这种极端集中度 |
| `max_total_exposure`（总持仓上限） | 账户净值的 60%（含杠杆前保证金口径） | 留出足够缓冲应对连续保证金追加需求，避免总敞口过高导致波动放大时被动减仓 |
| `max_open_positions`（最大同时持仓数） | 3（第一阶段单品种场景下，指同品种不同策略/方向的并行持仓） | 限制多策略同时开仓造成的隐性总敞口失控 |
| `max_leverage`（最大杠杆） | 3 倍 | AGENTS.md 强调风控优先，永续合约常见的 10 倍以上杠杆在本平台第一阶段不适用；3 倍是"仍能获得一定资金效率但爆仓距离足够远"的保守选择 |
| `daily_loss_limit`（当日最大亏损） | 账户净值的 3%，触发后当日剩余时间暂停新开仓 | 与"单笔 1%"配合，意味着当日最多容许约 3 次满额亏损的信号后即暂停，防止连续误判在同一天内累积成重大损失 |
| `weekly_loss_limit`（单周最大亏损） | 账户净值的 8%，触发后暂停新开仓直到人工复盘确认恢复 | 单周阈值高于单日阈值的简单叠加（3%×5≈15%），因为分散在多日发生的亏损性质上比单日集中亏损风险更低，允许更宽松一些，但仍需人工介入而非自动恢复 |
| `drawdown_limit`（最大回撤保护，触发降级） | 账户净值较近期峰值回撤 10%，触发 `reduce_exposure`（收紧后续新仓位规模，不强制平仓已有持仓） | 呼应 Validation Layer 门槛"Max Drawdown < 25%"是策略准入门槛，此处是实盘运行时的动态保护，数值更保守，因为实盘保护要在策略级门槛被突破之前就先反应 |
| `hard_stop_drawdown_limit`（硬停止回撤） | 账户净值较近期峰值回撤 20%，触发 `hard_stop`，停止全部新开仓，需人工确认后才能恢复 | 低于 Validation Layer 的 25% 策略淘汰门槛，确保实盘账户级熔断总是先于"策略被证明彻底失效"这个更严重的判断触发，给人工留出介入窗口 |

以上数值均针对 BTC/USDT 永续这一第一阶段主市场设定。扩展到其他市场（ETH/SOL/
A股/美股/黄金/纳指）时，不应直接复用这组数值——不同市场的波动率特征、杠杆惯例、
保证金规则都不同，扩展市场的阈值应在对应市场接入时重新评估，本文件只对当前
第一阶段主市场给出裁决。

## 05 裁决四：熔断触发规则的具体化

补全 `execution-risk-review-design.md` §2.2a 留白的新闻分级暂停时长，以及连续亏损/
API 连续失败等规则族的具体触发条件：

| 风控规则族 | 触发条件（具体化） | 触发后动作 | 恢复条件 |
|---|---|---|---|
| 连续亏损保护 | 同一策略连续 4 笔亏损信号 | `pause_strategy`（仅该策略暂停新开仓，不影响其他策略） | 人工复盘确认后手动恢复，不自动恢复 |
| 极端回撤熔断 | 见 §04 `hard_stop_drawdown_limit` | `hard_stop` | 人工确认 |
| 高严重度新闻/宏观事件暂停 | `RiskEvent.severity=high` | 暂停新开仓 30 分钟（BTC/USDT 永续场景下的默认值，可配置），已有持仓止损上移/下移收紧至距当前价更近的位置（具体收紧比例建议 30%，即止损距离缩短至原距离的 70%） | 30 分钟计时结束且期间无新的 high severity 事件则自动解除暂停（**这是本文件唯一允许自动恢复的场景**，理由见下方说明） |
| `critical` 严重度事件（如交易所暴雷/稳定币脱锚） | `RiskEvent.severity=critical` | `hard_stop`，停止该交易所/该资产全部新开仓 | 人工确认，不自动恢复 |
| API 连续失败停机 | 同一交易所连接在滚动窗口内（如 10 分钟）重连失败超过 5 次，或 §02 所述 LLM 超时否决连续超过 5 次 | `pause_account`（该交易所账户级暂停） | 人工确认，需先完成 `24x7-operations-plan.md` §2.2 的重连后一致性核对 |
| 数据中断禁开仓 | A 级行情数据最近一条更新时间超过阈值（如 2 分钟无新数据） | `pause_strategy`（暂停依赖该数据的策略） | 数据恢复且完成一次新鲜度确认后自动解除（同高严重度新闻场景一样属于"检测条件本身可信、恢复不依赖人工判断"的例外） |

**关于自动恢复的例外说明**：`24x7-operations-plan.md` §4.2 已确立"自动降级、人工
恢复"为默认原则，本文件在"高严重度新闻事件计时结束"与"数据中断恢复"两种场景下
给出例外，因为这两种场景的恢复条件是**客观、可验证、无歧义**的（"30 分钟已过且
无新事件"、"数据流已恢复且新鲜度确认通过"），不依赖人工判断信息是否可靠。而
"连续亏损"、"回撤熔断"、"API 连续失败"这几类场景的恢复需要判断"问题是否已经
真正解决"，这类判断具有主观性，必须人工确认。这一区分本身就是裁决的一部分——
不是所有降级场景都同等地需要人工恢复，但默认原则仍是"需要人工"，只有明确列出
的例外才允许自动恢复。

## 07 P0/P1 边界

- P0：本方案文档产出；`RiskProfile` 阈值默认值确定。
- P1：`RiskProfile` 已代码化并可持久化，后续重点是把默认阈值配置化接入 Risk Engine
  的实际判断逻辑；启动期 Key 权限自检实现；LLM 超时否决判定逻辑接入 Decision Veto
  Agent 调用封装；§05 熔断规则表格实现为 Risk Engine 的判断规则。
- P2：跨市场扩展时的阈值重新评估（§04 已声明不在本轮裁决范围）；熔断规则的
  动态自适应调整（如根据近期波动率自动调整阈值，当前仍是静态配置）。
