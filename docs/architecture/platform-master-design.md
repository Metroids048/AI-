## 01 产品定位

### 1.1 平台为什么存在

本平台存在的目的，不是预测市场涨跌，也不是输出买卖建议，而是帮助研究者建立一套可重复、可验证、可复盘、可迭代的量化研究系统。

核心问题不是“今天买什么”，而是：

- 如何把交易直觉转成可执行规则
- 如何快速验证一个假设是否有统计意义
- 如何让策略失败后留下可复用知识
- 如何用统一平台管理策略、回测、模拟盘、风控和复盘

### 1.2 与相邻产品的边界

本平台不是：

- 荐股工具
- 自动喊单工具
- 情绪化预测工具
- 面向公众的投顾产品
- 只会跑回测的单脚本系统

本平台是：

- 面向个人/小团队内部使用的研究台
- 以策略研究闭环为核心的内部工作系统
- 用 AI 提升研究、规则化、编码、分析、复盘效率的基础设施

### 1.3 核心目标

第一目标是把以下闭环做实：

`交易假设 -> 规则化 -> 历史回测 -> 模拟盘 -> 小资金实盘验证 -> 复盘 -> 迭代`

第二目标是把策略资产、失败记录、研究过程沉淀为长期可检索知识。

### 1.4 非目标

P0 非目标明确如下：

- 对外 SaaS 化
- 多租户
- 商业化计费
- 复杂 RBAC
- 面向公众的产品包装
- 真正的全市场统一执行系统
- 绕过人工审核的高风险自动化

## 02 用户与工作流

### 2.1 目标用户

第一版只服务于内部研究台场景：

- 你本人
- 小团队研究协作

不按外部海量用户产品设计。

### 2.2 研究员视角的一天

典型日工作流应为：

1. 提出一个新的交易假设
2. 用 Strategy Agent 将假设规则化
3. 审核策略草案是否符合研究意图
4. 进入历史回测与参数优化
5. 查看回测报告与样本外结果
6. 只有达标策略才能进入模拟盘
7. 每日查看 Review Layer 生成的日报与失效模式
8. 决定继续、暂停、调参还是淘汰

### 2.3 人工决策点

平台必须保留明确人工审核点：

- 假设是否进入规则化
- 规则化结果是否进入编码/回测
- 回测达标策略是否进入模拟盘
- 模拟盘稳定后是否进入小资金实盘
- 风控熔断后是否恢复
- 策略是否继续、暂停、淘汰或版本迭代

AI 可以提建议，但不能越过这些人工关口。

## 03 六层架构总览

### 3.1 Data Layer

职责：

- 统一接入五级数据源
- 做时间对齐、标准化、缓存、存储和来源追踪
- 为上层提供稳定的引用数据与事件输入

输入：

- 市场数据、宏观事件、新闻、社媒事件、研究资料

输出：

- 标准化市场数据流
- 风险事件原始输入
- 研究资料元数据

禁止越权：

- 不直接做交易决策
- 不直接修改策略状态

### 3.2 Strategy Layer

职责：

- 统一管理策略知识库与策略生命周期
- 存储策略定义、来源、版本、失败原因和状态

输入：

- 用户提出的交易假设
- Research Agent 发现的新策略来源
- Review Layer 回写的失败和迭代信息

输出：

- 结构化策略对象
- 待编码/待回测/待模拟盘策略任务

禁止越权：

- 不直接执行交易
- 不绕过验证层升级策略状态

### 3.3 AI Agent Layer

职责：

- 将 AI 能力拆成清晰的研究分工
- 用结构化任务驱动规则化、编码、分析、分类和复盘

输入：

- 策略对象、研究源、风险事件、回测/交易结果

输出：

- 结构化草案、代码工件、风险标签、复盘结论、研究摘要

禁止越权：

- 不直接下单
- 不直接通过自然语言修改核心状态

### 3.4 Validation Layer

职责：

- 回测
- 参数优化
- 样本外验证
- 模拟盘
- 小资金实盘准入控制

输入：

- 策略定义
- 历史数据
- 风险与配置参数

输出：

- 验证报告
- 准入/拒绝结论
- 模拟盘与实盘候选状态

禁止越权：

- 不直接沉淀最终复盘知识
- 不直接替代 Risk Engine

### 3.5 Execution Layer

职责：

- 执行订单路由
- 处理交易确认、止损、止盈、撤单、异常重试
- 联合 Risk Engine 控制执行权限

输入：

- 已通过验证层的策略信号
- 风险参数与事件开关

输出：

- 订单执行记录
- 持仓状态
- 执行异常事件

禁止越权：

- 不允许无止损执行
- 不允许忽略风险熔断

### 3.6 Review Layer

职责：

- 每日复盘
- 识别失效模式
- 生成继续/暂停/淘汰建议
- 回写失败记录和迭代历史

输入：

- 回测报告
- 模拟盘/实盘结果
- 风险事件

输出：

- 日报
- 策略诊断
- 知识沉淀

禁止越权：

- 不直接执行交易
- 不直接改写历史事实数据

## 04 项目结构与技术路线

### 4.1 单仓结构

本平台采用单仓组织，理由是：

- 当前是内部研究台，不需要一开始拆成多仓
- 领域对象高度耦合，统一版本管理更稳
- 便于同步维护文档、后端、前端、任务流和配置

建议结构：

```text
apps/
  api/
frontend/
  admin/
services/
  data/
  strategy_library/
  agents/
  validation/
  execution/
  review/
research_source/
  worldquant_adapter/
docs/
tests/
```

### 4.2 技术路线

后端：

- `FastAPI` 作为平台接口层
- `PostgreSQL` 作为事实存储与策略/报告主库
- `Redis` 作为缓存、短期状态与任务协调辅助
- `Celery + Redis` 作为异步任务基础

量化与交易：

- `CCXT` 负责交易所统一适配
- `Freqtrade` 优先承担加密策略研究、回测、模拟盘基础能力
- `Backtrader / VectorBT` 为未来多市场与更灵活研究留接口

AI 与知识：

- `Claude API` 负责 Agent 能力
- `LangChain / LlamaIndex` 负责 RAG 与知识检索层

前端：

- `React + Tailwind` 作为管理后台

### 4.3 P0 必需与预留能力

P0 必需：

- FastAPI
- PostgreSQL
- Redis
- Celery
- CCXT
- Freqtrade
- React + Tailwind

P1/P2 预留：

- 更复杂的多市场回测引擎组合
- 更完整的研究知识检索系统
- 更复杂的实时事件分析 Agent

## 06 数据源接入总策略

### 6.1 五级数据源框架

平台从总设计层面完整支持五级数据源：

- `A级市场数据`
- `B级宏观数据`
- `C级新闻数据`
- `D级社媒数据`
- `E级研究数据`

### 6.2 分阶段启用原则

本平台采用“接入框架先定，真实接入分阶段启用”的策略：

- `P0` 真正上线 `A级`
- `B/C/D/E` 在 P0 中先明确：
  - 接入协议位置
  - 调度位置
  - 存储位置
  - 风险标签链路
  - 研究来源链路

但不要求 P0 全量实时在线。

### 6.3 数据源作用边界

- `A级` 可直接进入策略研究与验证输入
- `B/C/D` 主要先作为风险标签和风险开关输入
- `E级` 只作为研究来源和策略灵感来源，不直接影响执行层

## 07 运行与治理原则

### 7.1 人工审核优先

以下环节必须保留人工确认：

- 策略草案进入编码/回测
- 策略进入模拟盘
- 策略进入实盘
- 熔断恢复
- 策略淘汰与版本升级

### 7.2 失败记录优先级

失败记录是核心资产之一。

每次策略失效、回测不达标、模拟盘偏差、实盘异常，都必须沉淀为：

- 可检索失败记录
- 可追溯版本历史
- 可被 Review/Research/Strategy Agent 复用的知识

### 7.3 配置与环境隔离

- 研究、模拟盘、实盘必须逻辑隔离
- 环境变量、交易所凭据、数据库连接必须分层隔离
- 风险开关必须有统一入口和审计记录

### 7.4 风险开关原则

任何执行自动化都受：

- Validation Layer 准入控制
- Risk Engine 风险约束

双重限制。

任何一层拒绝，执行不得继续。

## 结论

P0 的目标不是一次性做完整终态，而是把内部研究台的最小闭环和架构母体定稳：

- 先稳住六层架构
- 先稳住主市场
- 先稳住研究闭环
- 先稳住策略库、验证层、风控层、复盘层
- 再让多数据源、多 Agent、多市场逐步进入
