# 24 小时自动实时交易运行方案

## 文档定位

本文件是开发前文档包的第 6 份，回答"模拟盘/实盘 7x24 不间断运行时，如何保证系统本身
不因为网络中断、进程崩溃、数据静默中断等技术故障而做出错误或危险的行为"。

本文件关注**运行时可靠性**，不重复裁决业务风控规则的取值（那是风控措施与保障方案文档
的职责），也不重复裁决部署拓扑（那是 `technical-architecture-plan.md` 的职责）。
两者的关系：本文件定义"系统检测到异常后应该做什么类别的动作"（如"暂停新开仓"），
风控方案文档定义"这个动作背后的阈值和权限细节"（如"暂停多久、由谁恢复"）。

本文件引用并遵守：`execution-risk-review-design.md`（硬拒绝规则/风险事件分级）、
`agent-and-orchestration-design.md`（Decision Veto Agent 同步调用位置）、
`llm-integration-plan.md` §3.2/§5（LLM 超时降级策略）、AGENTS.md 不可谈判项
（"没有止损的单子拒绝执行"等）。

---

## 01 运行时监督的分层模型

24 小时运行的可靠性问题分三个层次，必须分层设计，不能混为一个"心跳检测"就完事：

| 层次 | 关注对象 | 典型故障 | 检测手段 |
|---|---|---|---|
| 进程层 | `api`/`celery_worker`/`celery_beat`/`freqtrade` 容器本身 | 容器崩溃、OOM、部署环境重启 | Docker Compose `healthcheck` + 容器自动重启策略 |
| 连接层 | 交易所 WebSocket/REST 连接 | 网络中断、交易所维护、连接假死（socket 未断但无数据流入） | 心跳/ping-pong 机制 + 数据流速监控 |
| 数据层 | 行情/资金费率/订单簿等数据流的连续性 | 数据延迟、数据缺口、数据源返回异常值 | 数据时间戳新鲜度检查 + `IngestionJob` 状态巡检 |

三层故障的处理动作强度递增：进程层故障优先自动重启恢复；连接层故障先尝试重连，
重连失败次数超限才升级为风险事件；数据层故障即使连接本身正常，也应触发"数据不可信"
的保守动作（如暂停新开仓），因为数据缺口对交易决策的危害不亚于连接中断。

## 02 连接层：心跳与重连设计

### 2.1 心跳检测原则

参考主流交易所 WebSocket API 的通行做法（如 Kraken 文档明确指出"定期心跳消息，
若停止收到心跳则认为连接已死"[Kraken Reconnection Guide](https://docs.kraken.com/exchange/guides/websockets/reconnection)；
业界普遍采用客户端发起的 ping/pong 双向心跳机制来检测"socket 看起来还开着但实际已无响应"
这种静默断连情况），本平台的心跳设计原则：

- **不能只依赖 TCP 连接状态判断是否在线**——连接层故障最危险的情况是"连接对象仍显示已连接，
  但实际已无数据流入"（静默断连）。必须用应用层心跳/数据新鲜度来判断，而不是底层 socket 状态。
- 心跳/数据新鲜度检查的具体间隔（多少秒判定为异常）是 Phase 1 实现参数，需按各交易所
  实际推送频率校准，本文件不预设固定数值。
- 若交易所原生提供 ping/pong 心跳帧，优先使用其原生机制；若没有，则以"最近一条行情/
  订单更新消息的时间戳"作为替代心跳信号。

### 2.2 重连策略

采用指数退避 + 随机抖动（jitter）的重连策略（业界通行做法，避免大量客户端同时重连时
对交易所形成瞬时压力，也避免因固定间隔重连撞上交易所限流窗口）：

```
重连间隔 = min(初始间隔 × 2^重试次数, 最大间隔上限) × (1 ± 抖动比例)
```

具体初始间隔、最大间隔上限、抖动比例数值属于 Phase 1 实现参数。设计要求是：

- 重连尝试必须有次数或时长上限，超限后不能无限重试到"看起来还在尝试恢复"实际上早已
  失去时效意义——超限后必须升级为 `RiskEvent`（`event_type=api_failure`），进入 §04
  的降级流程，而不是静默无限重试。
- 每次重连成功后，必须先做一次数据一致性核对（如拉取最新持仓快照与本地记录比对），
  才能恢复正常交易，不能"连上了就立刻恢复开新仓"——断连期间可能发生了平台未感知到的
  订单成交/强平。

### 2.3 Freqtrade 层面的现状与承接

当前 `docker-compose.yml` 中 `freqtrade` 服务的 `dry_run=true`（见技术架构方案 §02
现状盘点），交易所连接的重连逻辑由 Freqtrade 自身框架处理，平台不重新实现交易所协议层。
平台侧的职责是：监督 Freqtrade 服务本身的可用性（进程层，见 §03），以及消费 Freqtrade
暴露的状态（如通过其 REST `:8080` 接口查询运行状态），不越权直接操作交易所连接。

## 03 进程层：容器监督与自动恢复

### 3.1 健康检查设计

沿用 `docker-compose.yml` 已有的 `depends_on` 健康检查模式（`timescaledb`/`redis`
已有 healthy 检查），Phase 1 需要为以下服务补充健康检查端点：

| 服务 | 健康检查方式（现状/规划） | 补充建议 |
|---|---|---|
| `api` | 已有 `/health` 端点（见技术架构方案 §04），但未接入 Docker `healthcheck` 指令 | Phase 1 补充 `HEALTHCHECK` 指令调用该端点 |
| `celery_worker` | 无 | 补充 `celery inspect ping` 作为健康检查命令 |
| `celery_beat` | 无 | Beat 进程存活检查（无内建健康检查命令，需自定义心跳文件或类似机制） |
| `freqtrade` | 有自身 REST 状态接口 | 平台侧巡检任务定期调用其状态接口，纳入本平台的 `IngestionJob`/监控体系 |

### 3.2 自动重启策略

- Docker Compose 层面为长驱动服务配置 `restart: unless-stopped` 或 `on-failure`
  （具体策略选择留给 Phase 1，因为不同服务的重启语义不同：`celery_worker` 崩溃后重启是安全的，
  但如果是执行链路中途状态导致的崩溃，需要先确认不会导致"部分执行"的订单状态不一致）。
- 自动重启不能掩盖故障——重启事件本身必须计入 §04 的异常计数，连续重启超过阈值应停止
  自动重启并升级为需要人工介入的风险事件，而不是无限自动重启形成"看起来在运行但反复崩溃"
  的隐性故障。

## 04 降级策略：从"正常"到"只允许平仓"

### 4.1 降级级别定义

呼应 `execution-risk-review-design.md` 的风险结果分类（`allow`/`deny`/`reduce_exposure`/
`pause_strategy`/`pause_account`/`hard_stop`），运行时故障对应的降级级别：

| 故障类别 | 对应风险结果 | 具体行为 |
|---|---|---|
| 单次连接抖动（重连成功） | `allow`（无降级） | 正常运行，但记录一次连接抖动事件供复盘统计 |
| 连接持续异常（重连超限） | `pause_strategy` 或 `pause_account`（视影响范围） | 暂停受影响策略/账户的新开仓，已有持仓保留但可考虑收紧止损（呼应新闻分级触发规则的处理模式） |
| 数据静默中断（心跳/新鲜度检查失败） | `pause_strategy`/`pause_account` | 暂停新开仓——数据不可信时，即使连接正常也不能基于过期数据做决策 |
| 交易所侧確認的系统性异常（维护/宕机公告） | `hard_stop` | 停止该交易所全部新开仓，已有持仓视具体情况人工决策是否强制平仓 |
| API Key 权限异常/账户异常 | `hard_stop` | 立即停止该账户全部交易活动，需人工介入 |

### 4.2 降级触发后的自动恢复边界

**自动降级、人工恢复是唯一允许的组合**——即降级动作（暂停/停止）可以由系统自动触发，
但从降级状态恢复到正常运行必须经过人工确认（呼应 PRD §03 六个人工决策点之一"风控熔断后
是否恢复"）。系统不允许"检测到连接恢复就自动解除暂停状态"，因为连接恢复不代表数据/
状态一致性已经过验证。

### 4.3 只允许平仓（close-only）模式

对于"账户/策略暂停新开仓但允许管理已有持仓"的场景，需要明确定义"只允许平仓"模式的具体行为：

- 已有持仓的止损/止盈单继续有效，不因降级而撤销（撤销止损单等于放大风险，与
  AGENTS.md"禁止取消机器人止损"直接冲突）。
- 允许的操作仅限于：正常止损触发、正常止盈触发、人工发起的主动平仓。
- 不允许的操作：开新仓、加仓、修改止损为更宽松的价格。
- 该模式的退出（恢复正常开仓）需要人工确认（§4.2）。

## 05 定时任务与维护窗口

### 5.1 Celery Beat 任务的可靠性要求

承接 `technical-architecture-plan.md` §06 的队列/Beat 规划，运行时可靠性层面的补充要求：

- 所有定时任务（数据同步、复盘生成、风险巡检、持仓快照）必须幂等，重复触发不产生重复副作用
  （已在技术架构方案 §06.3 定义，本文件强调这一要求对 7x24 运行尤为关键：Beat 进程重启后
  可能出现任务重复排队）。
- 关键定时任务（尤其是风险规则巡检）如果错过执行窗口（如 Beat 进程短暂不可用），
  必须有补偿机制（下次巡检时检测"距上次巡检时间过长"本身也应被视为一种异常信号）。

### 5.2 维护窗口设计

- 平台自身的维护操作（数据库迁移、依赖升级、配置变更）不能在"实盘/模拟盘持有未平仓位"
  的任意时刻执行，应设计明确的维护窗口触发条件：无未平仓位，或已完成对未平仓位的
  风险隔离处理（如临时切换为只允许平仓模式）。
- 交易所自身的维护窗口（多数交易所会提前公告）应作为已知的计划性降级事件处理，
  与突发故障区分：计划性维护可以提前主动切换为 `pause_strategy`，不需要等到连接异常
  才被动触发。

## 06 通知与告警触发规则

### 6.1 现状与依赖

技术架构方案 §09 已登记：当前仓库内没有任何出站通知机制。本节定义触发规则本身
（"什么情况下要通知"），具体推送渠道实现（Telegram Bot/邮件/Webhook）由 Phase 1
补齐，可参考成熟交易机器人生态中常见的"Bot 主动推送运行状态"模式，但用途严格限定为
出站告警，不与 D 级数据源的 Telegram 采集链路复用同一 Bot Token（呼应技术架构方案 §09）。

### 6.2 触发规则分级

| 级别 | 触发条件 | 通知时效要求 |
|---|---|---|
| 紧急 | `hard_stop` 级别降级、API Key 权限异常、连续重启超限 | 尽快触达（具体延迟上限留给实现，原则是"分钟级"而非"等下次查看界面才知道"） |
| 重要 | `pause_strategy`/`pause_account` 级别降级、high severity `RiskEvent`、Decision Veto Agent 否决率异常升高 | 及时触达，不要求秒级 |
| 常规 | 每日复盘日报生成完成、模拟盘/实盘状态定期摘要 | 按固定节奏推送，不要求即时性 |

### 6.3 通知内容要求

- 必须包含：触发时间、触发原因分类、当前系统降级级别、受影响范围（策略/账户/交易所）、
  建议的人工操作（若有）。
- 不能只发"系统异常"这种无法据此行动的通知——呼应 PRD §4.5 风控模块验收标准
  "熔断状态必须清晰展示触发原因"，通知内容应与界面展示的信息结构一致，不能是两套口径。

## 07 运行时状态的可观测性

### 7.1 关键运行时指标（呼应技术架构方案 §09 的 Prometheus/Grafana 规划）

7x24 运行需要持续观测的指标类别（不细化具体指标名，具体指标留给 Phase 1/2 实现）：

- 连接层：当前各交易所连接状态、最近重连次数、心跳/数据新鲜度延迟。
- 进程层：各服务容器的重启次数、健康检查失败次数。
- 执行层：信号生成到执行完成的延迟分布、Decision Veto Agent 调用延迟与超时率
  （呼应 `llm-integration-plan.md` §3.2）。
- 数据层：各 `IngestionJob` 的最近一次成功时间、数据缺口计数。

### 7.2 与 Review Layer 的关系

运行时可靠性事件（连接抖动、降级触发、自动恢复）本身也应作为 Review Layer 每日复盘的
输入之一，但属于"平台运维视角"的复盘，与"策略表现"视角的复盘是两条不同的分析维度
（呼应 `llm-integration-plan.md` §4.4 "运维成本报表不应与策略复盘报告混在一起"的原则，
此处延伸为同一原则也适用于可靠性事件）。

## 08 P0/P1 实现边界

- P0：本方案文档产出。当前 `dry_run=true` 的 Freqtrade 骨架已存在，不要求任何可靠性
  机制代码化。
- P1：健康检查端点补全（§03.1）、基础重连/退避逻辑（若平台自建 WebSocket 消费者，
  Freqtrade 自身连接由其框架处理）、降级状态机实现（§04）、通知触发规则实现（依赖
  技术架构方案 §09 的通知层）。
- P2：维护窗口自动化编排（§05.2）、更完整的可观测性指标体系（§07.1）。
