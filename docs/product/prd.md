# 产品需求文档（PRD）

## 文档定位

本文件是开发前文档包的第 2 份，承接 [product-spec.md](product-spec.md)（产品定位/边界）与
[feature-catalog.md](feature-catalog.md)（功能清单总表），把它们展开为可用于开发排期和验收的

真源关系：本文件服从 `product-spec.md` 的产品定位和非目标；与 `feature-catalog.md` 的功能项
一一对应，不新增未在功能清单总表中出现的功能大类；与 `phase-roadmap.md` 的阶段划分保持一致。

## 01 产品愿景与成功标准

### 1.1 愿景

把"交易假设 -> 规则化 -> 历史回测 -> 模拟盘 -> 小资金实盘 -> 复盘 -> 迭代"这条研究闭环，
变成一个研究者每天都会打开、依赖它做决策留痕的内部工作台，而不是一套用完即弃的脚本集合。

### 1.2 产品成功的标准（不是收益指标）

本产品的成功标准**不是**"跑赢大盘"或"月化收益率"，因为 AGENTS.md 明确 AI 的职责是研究，
不是主观预测涨跌。产品层面的成功标准是：

- 一个新的交易想法，从提出到拿到第一份历史回测报告的平均耗时可测量、可缩短。
- 每一次策略失效都能沉淀为可检索的 `FailureRecord`，且能被下一次策略设计复用（不是每次从零分析）。
- 没有一笔实盘/模拟盘订单绕过验证层和风控层出现（这是可审计的硬指标，见 §07 验收标准）。
- 研究者可以在不打开代码/数据库的情况下，通过管理台看清楚"现在有哪些策略、分别在什么状态、
  为什么暂停或淘汰"。

### 1.3 反成功标准（明确不追求）

呼应 `product-spec.md` 的非目标：不追求用户增长、不追求对外产品化体验、不追求"AI 直接给出
买卖建议"的即时满足感。如果某个功能设计是为了让 AI 更快给出交易结论而弱化人工审核点，
即视为偏离产品目标，应被拒绝（对应 §03 人工决策点的硬约束）。

## 02 用户与角色

### 2.1 角色定义

产品目前只定义两类角色，不做复杂 RBAC（P0/P1 非目标）：

| 角色 | 描述 | 典型操作 |
|---|---|---|
| 研究者（Researcher） | 平台的主要使用者，可能是用户本人或小团队协作者 | 提出假设、审核草案、查看回测/复盘、决定策略晋升/暂停/淘汰 |
| 系统/Agent（System） | 11 个 AI Agent 及调度系统本身 | 结构化假设、生成代码、执行回测、生成复盘、发出风险事件与否决建议 |

不存在"管理员管理其他用户"场景，因为这是内部研究台，不是多租户 SaaS。

### 2.2 研究者的一天（用户旅程，承接 platform-master-design.md §2.2 并展开为可验收步骤）

1. 打开管理台，查看策略库总览和昨天的复盘日报。
2. 提出一个新的交易假设（自然语言或结构化表单）。
3. 触发 Strategy Agent 把假设规则化为 `StrategyDraft`，研究者审核草案是否符合本意。
4. 确认草案后，触发编码 + 历史回测，等待/查看 `BacktestRun` 结果和样本外验证结果。
5. 若达标，决定是否放入模拟盘；若不达标，查看失败原因，决定调参重试还是放弃。
6. 模拟盘运行期间，每日查看运行状态、风险事件、Decision Veto Agent 的否决记录（若有）。
7. 模拟盘稳定后，决定是否进入小资金实盘（人工关口，AI 不能越过）。
8. 每日查看 Review Layer 日报，决定策略继续/暂停/调参/淘汰。
9. 熔断触发后，查看熔断原因，决定是否人工恢复。

## 03 人工决策点（产品硬约束）

以下 6 个决策点必须由研究者在界面上明确操作（点击确认/拒绝），系统不得自动越过，
AI 只能提供建议文本，不能自动执行：

1. 假设是否进入规则化
2. 规则化结果（`StrategyDraft`）是否进入编码/回测
3. 回测达标策略是否进入模拟盘
4. 模拟盘稳定后是否进入小资金实盘
5. 风控熔断后是否恢复
6. 策略是否继续、暂停、淘汰或版本迭代

产品设计要求：界面上这 6 个决策点必须有**独立的、不可被批量默认确认掩盖**的操作按钮
（不能设计成"全部通过"的批量勾选框，避免研究者习惯性无脑点通过而让人工关口形同虚设）。

## 04 模块级用户故事与验收标准

本节按 `feature-catalog.md` 的模块划分，逐模块给出用户故事和验收标准。字段级 API 细节见
`technical-architecture-plan.md` §05，本节只关注用户可观察的行为。

### 4.1 研究入口

**用户故事**：作为研究者，我希望能录入一个交易假设，并知道它接下来会发生什么，
这样我就不用去问系统在后台做了什么。

验收标准：
- 可以通过表单录入假设，至少包含：假设描述（自由文本）、来源标签（人工/WorldQuant/GitHub/
  论文/A股系统等）、初步市场范围。
- 提交后能看到假设当前状态（如"待规则化"），状态变化对研究者可见（不需要看日志）。
- 假设一旦被规则化为 `StrategyDraft`，原始假设文本仍可追溯查看（不会被覆盖丢失）。

### 4.2 策略库

**用户故事**：作为研究者，我希望随时能看到所有策略当前处于什么状态、经历过什么版本变化、
为什么失败过，这样我做新决策时不用凭记忆。

验收标准：
- 策略列表可按状态（drafting/backtesting/paper/live/paused/retired 等，具体枚举见
  domain-and-interfaces-design.md）筛选。
- 每个策略详情页能看到完整版本历史（`StrategyVersion`）和每个版本对应的验证结果链接。
- 每个策略若有 `FailureRecord`，必须能在详情页直接看到失败原因文本，不需要跳转到其他系统。
- 策略详情页能看到当前是否命中相关性过滤（是否与其他在跑策略高度相关，见
  appendix-b-feature-phasing.md P1 排序）。

### 4.3 验证（回测/优化/样本外/模拟盘准入）

**用户故事**：作为研究者，我希望回测报告能直接告诉我这个策略是不是在"撞大运"，
而不是只看一个好看的 Sharpe 数字。

验收标准：
- 回测报告展示：原始 Sharpe、Deflated Sharpe（若已计算）、`trials_count`、Profit Factor、
  Max Drawdown、Expectancy、`total_cost_bps`（净成本影响）、样本外验证结果、
  已覆盖的压力测试场景列表（`luna_collapse_2022_05`/`black_thursday_2020_03`/
  `exchange_outage`/`extreme_wick`）及各场景下的表现。
- 若某策略的压力测试覆盖不足或未达 AGENTS.md 门槛（`Sharpe > 1.0`、`Profit Factor > 1.3`、
  `Max Drawdown < 25%`、`Expectancy > 0`，且优先看 Deflated Sharpe 而非原始 Sharpe，
  见 validation-methodology.md §05），界面必须明确展示"不达标"或"条件通过需人工复核"，
  不能只显示一堆数字让研究者自己心算是否达标。
- 参数优化任务的结果需展示参数敏感性（不同参数组合下指标的分布），避免"过拟合到单一最优参数"
  被误当作稳健结果。
- 模拟盘准入按钮只有在验证结论为"达标"或"条件通过+人工已确认"时才可点击。

### 4.4 执行（模拟盘/实盘）

**用户故事**：作为研究者，我希望能实时看到模拟盘/实盘的运行状态和每一笔订单为什么被执行或拒绝，
这样我能在出问题前发现异常，而不是事后从日志里排查。

验收标准：
- 运行视图展示当前持仓、近期订单、每笔订单的执行前置检查结果（是否通过 SignalEnsemble/
  MetaLabel、是否被 Decision Veto Agent 否决、是否有止损计划）。
- 被拒绝的信号必须展示拒绝原因（对应 execution-risk-review-design.md §1.4 硬拒绝规则或
  Decision Veto Agent 的 `veto_reason`），不能只显示"未执行"。
- 实盘运行视图与模拟盘运行视图使用同一套 UI 组件（不重复开发两套），但必须有清晰的视觉区分
  （如实盘用红色边框/明显标识），避免研究者误将模拟盘当实盘或反之。

### 4.5 风控

**用户故事**：作为研究者，我希望能配置风险规则、看到风险事件流、并在熔断发生时第一时间知道，
这样我不需要一直盯着屏幕。

验收标准：
- 风险规则配置界面覆盖 execution-risk-review-design.md §02 列出的规则家族
  （单笔风险/单品种持仓/总持仓/最大并发/最大杠杆/日周最大亏损/连续亏损/最大回撤/极端回撤熔断/
  宏观新闻分级暂停/稳定币异常/API连续失败/数据中断）。
- 风险事件流按 `severity` 分级展示（high/mid/low），high 级事件必须有醒目的视觉提示。
- 熔断状态页面清晰展示：触发原因、触发时间、当前 `resolution_status`
  （`detected -> acknowledged -> mitigated -> resolved`）、恢复所需的人工操作。
- 高严重度事件触发后，即使研究者没打开界面，也应能收到主动通知（对应
  technical-architecture-plan.md §09 登记的通知层缺口，具体触发规则由
  "24 小时自动实时交易运行方案" 文档裁决，本文件只定义这是产品必须具备的能力）。

### 4.6 复盘

**用户故事**：作为研究者，我希望每天早上能用几分钟看完一份复盘日报就知道昨天发生了什么、
哪些策略需要关注，而不用自己重新跑一遍分析。

验收标准：
- 每日复盘日报包含：昨日运行策略清单、表现最差的策略及可能原因分类（市场因素/参数因素/
  执行因素/风控因素）、需要人工决策的建议清单（暂停/调参/淘汰）。
- 失败记录列表可检索（按策略/按失败原因分类/按时间范围），且明确标注该失败记录是否已被
  后续策略设计参考过（是否形成了知识复用闭环，即使 P0 阶段只是简单的"已读/引用"标记）。
- 复盘日报中若包含 LLM 生成的分析文本，必须明确标注"AI 生成"，且旁边展示其依据的原始数据来源，
  不能让研究者误以为是人工分析结论。

### 4.7 数据

**用户故事**：作为研究者，我希望能看到当前各级数据源的接入状态和数据质量，
这样我知道能不能信任基于这些数据做出的回测/风险判断。

验收标准：
- 数据源状态面板展示 A/B/C/D/E 五级数据源的接入状态（在线/离线/框架预留未启用），
  与 platform-master-design.md §6.2 的分阶段启用原则一致，未启用的数据源明确标注
  "框架已就位，暂未接入"，不能伪装成"已接入但无数据"。
- A 级市场数据需展示数据延迟/缺口检查结果（对应 Makefile 中 `data-check` 目标，Phase 1 实现）。

## 05 非功能需求

### 5.1 可靠性

- 数据中断、交易所 API 连续失败必须触发降级（自动转为只允许平仓/不开新仓），
  不能因为数据/API 异常而让持仓处于"无人管理"状态（对应 execution-risk-review-design.md
  硬拒绝规则）。
- 系统重启/服务重启不能丢失进行中的策略状态、持仓状态、风险事件记录
  （数据落库到 PostgreSQL/TimescaleDB，不依赖内存态，除非明确标注为"内存 seam，Phase 1 前替换"）。

### 5.2 可审计性

- 任何影响执行的决策（策略晋升、风险熔断、Decision Veto Agent 否决、人工恢复熔断）
  必须留存操作者（人工或系统）、时间、原因三要素，可回溯查询。
- LLM 输出（否决理由、复盘文本）必须留存原始输出，不能事后被覆盖或静默修改。

### 5.3 可用性（界面）

- 六大人工决策点（§03）在界面上必须有清晰的、不易误操作的独立入口。
- 关键数字（回测指标、风险阈值、账户权限状态）不允许因为界面加载失败而"默默显示为 0
  或空白误导为正常"，加载失败必须显式提示"数据加载失败"而非展示误导性默认值。

### 5.4 性能（P0/P1 范围内的合理要求，不做过度设计）

- 策略库列表/详情、回测报告查看等只读页面，在数据量为 P0/P1 预期规模（数十到数百个策略、
  数千次回测记录）下应能正常交互，不需要为未来海量数据做提前优化。
- 实盘/模拟盘运行视图的持仓/订单状态刷新延迟应在可接受范围内（具体数值留给
  "24 小时自动实时交易运行方案" 文档裁决,本文件只提出"不能明显滞后到影响风险判断"的定性要求）。

## 06 范围外（Out of Scope，呼应 product-spec.md 与 appendix-c）

以下明确不在本 PRD 范围内，不接受"顺手加一个"式的范围扩展：

- 面向公众的荐股/跟单功能
- 多租户账户体系、复杂 RBAC
- 商业化计费/订阅
- 移动端 App（管理台仅覆盖 Web，P0/P1 范围内）
- 全市场统一执行网络（P0 明确非目标）
- 绕过人工审核的全自动高风险交易

## 07 验收标准总纲（可用于 Phase 1 结束时的整体验收）

Phase 1 结束时，以下用户旅程必须能被端到端走通一次（即使数据源/策略数量很少），
这是产品层面"最小闭环已打通"的验收标准：

1. 研究者录入一个假设 -> 系统生成草案 -> 研究者确认 -> 生成策略代码 -> 触发历史回测 ->
   查看含 Deflated Sharpe/成本建模/压力测试的回测报告 -> 研究者决定进/不进模拟盘。
2. 若进模拟盘：系统按信号融合 + MetaLabel 流程生成执行信号 -> Decision Veto Agent 复核 ->
   执行 -> 产生 `PositionSnapshot` -> 每日复盘生成日报。
3. 人为触发一次风险事件（如手动标记一次 high severity `RiskEvent`）-> 验证新开仓被暂停、
   已有仓位止损被收紧、事件在界面可见。
4. 人为让一个策略回测不达标 -> 验证其无法被点击"进入模拟盘"，且失败原因被记录进
   `FailureRecord` 并在策略详情页可查看。

这 4 条不是本文档裁决的具体测试用例，而是产品级验收的最低标准，具体测试实现留给开发阶段。
